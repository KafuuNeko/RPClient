# Issue #21 搜索存储优化实施与实机验证

> 日期：2026-10-18～19。当前搜索行为见[功能实施说明](./Issue-21-搜索功能实施与验证.md)，对照提交为 `c39aaff`。Room version 保持 **5**，修改未发布版本的结构。

## 实施内容

| 改动 | 目的与边界 |
| --- | --- |
| `search_chunks` 移除 `text`，只保留可逆 `tokens` | 不再保存第二份规范化正文；原始业务正文保留，当前结果页解码还原片段 |
| 分块改为 4,096 码点 | 减少块数、重叠和页开销；仍保留 127 码点重叠、128 码点查询上限 |
| 先聚合、排序和分页，再读取 token 与发言者 | 大字段只读取本批最多 21 个结果，避免候选集排序携带全部 token；仍遍历所有匹配候选，未截断搜索范围 |
| 替换与确认合并事务，写入按字节分批 | 短源通常一个事务完成；长源每批最多 16 块且编码量预算 128 KiB，最后一批才发布当前修订 |
| 串行回收删除标记、空闲合并与空间检查 | 避免状态行无限增长；不在用户查询路径执行全库整理 |

首页搜索按钮、独立搜索页、完整历史消息与故事正文搜索范围均保持现有行为。本次没有增加页面或用户文案，空间分项统计由显式启用的测试工具提供。

### 编码与恢复

`SearchTextCodec.decodeTokens` 按码点还原当前页内容，不为每个 token 创建独立字符串列表。它严格检查字面字符、十六进制范围、大小写和分隔符，损坏数据不会静默变成漏字。

`search_progress.kind = -1` 保存投影格式版本。格式不匹配时暂不返回旧正文索引，工作器原子失效源修订后逐源补建；标题查询和显式原文扫描仍可用。显式重试现在会从业务原文重新投影，可修复损坏的 token。

### 删除与并发

源删除后先由原触发器使旧修订失效，查询立即排除旧正文；工作器再删除对应块，Room 的 FTS 触发器同步处理倒排索引。

删除标记仅在历史播种完成、本批源快照已全部处理后回收。单条 SQL 同时复核 `deleted = 1`、`dirty = 0`、无关联块、业务源已不存在，每批最多 256 行。仍存在的 Summary 排除状态继续保留。新增 `(deleted, dirty, kind, sourceId)` 索引支持候选定位。

启动、停止、重试共用生命周期互斥锁，停止和重试等待旧工作器退出。这避免删除状态后同 ID 重用较低修订号时，旧快照再次提交。

### 空间维护

工作器在启动循环及非空批次写入前检查可用空间，约 65 MiB 以下暂停派生写入，每 10 秒重新检查。这个余量是保守保护阈值，不能保证磁盘耗尽时业务仍能写入，也不是完整重建的空间上界。

更新、删除后，以及进程重启后，工作器空闲时最多分八轮执行 `merge=64,2`。每轮之间让出执行机会；有待办时优先处理待办。它不是完整 FTS optimize，也不保证立即清空所有旧片段。

生产代码没有新增 `VACUUM`、强制 WAL 截断或更改 `auto_vacuum`。测试中的 checkpoint 只用于统一计量口径。设备默认 FULL 自动回收与之前桌面实验的 NONE 模式不同，不能套用桌面实验“删除后主文件不缩小”的结论。

## 实机测量方法

- 设备为已连接的 PKX110，SoC SM8750，Android API 36，系统 SQLite 3.44.3，页大小 4,096 字节。
- 使用 Debug 构建、独立测试应用包和专用合成数据库，不覆盖正式应用和真实聊天。Activity 保持前台与亮屏，降低后台冻结干扰。
- 100 MiB 组为 4,965 条重复中英、符号和 emoji 混合消息，原文 104,954,025 字节，分布在 1,000 个会话。500 MiB 组沿用相同生成器扩大消息数量。
- 查询计时覆盖完整 Repository 的 FTS 匹配、对象聚合、排序、分页和片段，不包含 UI 绘制。每词顺序采样 20 次，P95 取排序后第 19 个样本，保留所有样本。
- 用户要求按“当前设备性能 / 2”评估，因此同时记录实测耗时与 **耗时 × 2** 的保守估算；这不是实际限频，也不能替代真实低端机测试。

主库稳态统一在停止工作器、成功执行 `wal_checkpoint(TRUNCATE)` 后统计；保留 WAL、SHM、空闲页及 DBSTAT 表页分项。建索引峰值每 20 ms 采样三个文件长度之和，只是采样峰值，不代表瞬时峰值上界。

## 实测结果

### 100 MiB 同语料对照

**最终主库从 467.52 MiB 降为 347.44 MiB，减少 120.08 MiB／25.68%。** 搜索功能带来的主库增量从 365.71 MiB 降为 245.55 MiB，减少约 32.86%；主库总量仍约为原文的 3.47 倍，并非接近一份原文。

| 方案 | 索引后主库 | 建索引采样峰值 | 删除一半后主库 | 删除标记剩余 |
| --- | ---: | ---: | ---: | ---: |
| 原实现：text + tokens／2,048 | 467.52 MiB | 474.43 MiB | 262.63 MiB | 2,482 |
| 最终方案：tokens／4,096＋分页后读取 | 347.44 MiB | 351.39 MiB | 198.25 MiB | 0 |

最终方案索引前主库为 101.89 MiB，索引后块数从 29,790 降到 14,895。删除后保留 2,483 个业务源、7,449 块，删除标记为零。主库已缩小不代表 FTS 内部所有删除片段都已合并。

| 索引后表页分项 | 原实现 | 最终方案 |
| --- | ---: | ---: |
| 原始消息表（不含其普通索引） | 100.86 MiB | 100.86 MiB |
| search_chunks | 310.59 MiB | 194.08 MiB |
| 块普通索引合计 | 0.70 MiB | 0.36 MiB |
| FTS 内部表及索引 | 54.00 MiB | 50.85 MiB |
| search_sources 及其普通索引 | 0.27 MiB | 0.34 MiB |

表页分项来自 DBSTAT，不包含所有数据库结构与自动回收指针页，不能用未列全的行简单相加代替主文件长度。

### 查询与建索引时间

下表为 **P95 实测 ms／耗时 × 2 估算 ms**。100 MiB 的 500 ms 目标以右侧估算值验收。

| 查询 | 原实现 | 最终方案 |
| --- | ---: | ---: |
| `unique203boundary` | 27.24／54.49 | 30.42／60.83 |
| `雪乃` | 103.43／206.86 | 100.07／200.14 |
| `的` | 83.78／167.55 | 86.84／173.68 |
| `100%_` | 143.62／287.24 | 158.06／316.13 |

最终四类查询的估算 P95 为 **60.83～316.13 ms**，均低于 500 ms。并非所有查询都更快：符号查询较原实现实测增加 14.44 ms（约 10.1%），双字查询略有改善。更大的块与分页后读取同时生效，不能将差异单独归因于块大小。

| 建索引时间 | 原实现 | 最终方案 |
| --- | ---: | ---: |
| 实测 | 119.52 s | 119.80 s |
| 性能减半估算 | 239.04 s | 239.61 s |

最终建索引耗时与原实现基本相当。两种实现是顺序独立运行，电量、温度和缓存状态未严格控制，不将这一轮差异解释为稳定的建索引加速。最终等待条件额外确认工作器 Ready 状态；旧对照主要确认持久待办耗尽。

### 500 MiB 压力测试

500 MiB 合成正文为 **524,789,390 字节、24,825 条消息、1,000 个会话**。测试完整完成，所有查询结果数量断言通过；此项通过表示流程与结果断言成功，不表示全部查询达到 500 ms。

| 存储指标 | 结果 |
| --- | ---: |
| 索引前主库 | 508.00 MiB |
| 索引后主库 | 1,734.63 MiB |
| 建索引采样峰值（主库＋WAL＋SHM） | 2,120.03 MiB／约 2.07 GiB |
| 删除一半消息后主库 | 997.56 MiB |
| 删除后源／块／删除标记 | 12,413／37,239／0 |

大库建索引的临时占用明显高于稳态。128 KiB 只约束应用插入块的批次，不约束 FTS 内部合并、删除整条旧源、完整重建或整库 WAL 的峰值。空间预留不能仅按这一个批次预算估算。

| 查询 | P95 实测 | 性能减半估算 |
| --- | ---: | ---: |
| `unique203boundary` | 111.86 ms | 223.71 ms |
| `雪乃` | 362.79 ms | 725.57 ms |
| `的` | 280.87 ms | 561.75 ms |
| `100%_` | 1027.70 ms | 2055.40 ms |

**500 MiB 下，双字、单字和符号查询的减半估算超过 500 ms；符号查询达到约 2.06 秒。** 因此本轮结论是“100 MiB 初始目标达成，500 MiB 压力边界已量化”，不能宣称任意规模均可即时返回。当前独立搜索页继续保留执行中状态与取消路径。

若后续将 500 MiB 常见词也定为 500 ms 以内，需要继续针对 FTS 高频词位置列表、候选聚合和大库合并进行专项优化，或验证固定 SQLite／原生字符 tokenizer 路线；不应通过减少历史搜索范围或截取固定候选数掩盖延迟。

该轮建索引墙钟时间为 607.04 秒，其中包含后台停顿，**不作为有效速度数据**；JSON 中的两倍建索引耗时同样不用于验收。恢复前台后的巡检直到结束未再触发恢复操作，查询阶段没有观测到后台切换。未运行原实现的 500 MiB 对照，不能给出该规模的相对加速或节省率。

## 回归与限制

- JVM：309 项通过，包含 Unicode token 往返、损坏编码拒绝与跨块最长查询。
- 实机：21 项通过，包含搜索仓库 10 项、会话分页 4 项、概览 2 项、迁移 4 项和首页搜索到历史消息定位 1 项。
- 删除覆盖索引中删除、同 ID 替换与回收后重插、级联删除，以及 20 轮新建／删除后无残留块和无多余墓碑；保留仍存在的 Summary 状态。
- 恢复覆盖损坏 token、格式版本失效、长源编辑与重启，以及并发启动／停止／重试。

首次回归有一个用例在测试 Activity 不在前台后超时；测试夹具改为每项持有前台 Activity 后，完整 21 项重跑通过，生产逻辑未为此更改。较早的一次 4,096 基准被系统终止，退出记录为 `OTHER KILLS BY SYSTEM`，无有效结果，已排除。500 MiB 首轮因切到后台而暂停，已终止并重跑；重跑期间又发生一次后台停顿，随后恢复前台并每 3 秒巡检。该轮建索引墙钟耗时保留在原始 JSON 中，但不作为有效速度结论；查询阶段与存储结果单独判读。

20 轮增删验证了逻辑行回收与一致性，未测量长期循环时文件体积是否达到稳定上界。

尚未覆盖最低 API 26、真实低端机、低重复真实语料、强制磁盘耗尽、完整重建时的磁盘与内存峰值。连续热查询和重复合成语料只适合本次结构对照，不能承诺任意真实库都有相同节省率。

Room schema 仍为 5；旧的未发布开发版 v5 与本次结构哈希不同，不能直接沿用旧 v5 开发库。实机使用隔离包新建测试库，没有通过清空正式业务数据库处理这一差异。已发布旧版本到新 v5 的迁移另由迁移回归检查。

## 复现入口

- 基准：`ContentSearchBenchmarkTest`，仅指定 `runSearchBenchmark=true` 时启用；`benchmarkMiB` 支持 10 至 500，`benchmarkLabel` 标识构建。
- 存储分项：`SearchBenchmarkStorage`，JSON 输出到测试应用缓存的 `content-search-benchmark.json`；必须在测试成功后核对 label 再导出，避免误读上次结果。
- 正确性：`SearchTextCodecTest`、`ContentSearchRepositoryTest`、会话分页、概览、数据库迁移和 `ContentSearchFlowTest`。
