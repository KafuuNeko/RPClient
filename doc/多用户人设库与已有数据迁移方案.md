# 多用户人设库与已有数据迁移方案

用户人设、默认人设选择以及单聊、群聊、故事各自的绑定均已存入主 Room 库。设置页的默认选择用于预选新会话。已有会话按自己的 `userPersonaId` 读取，单聊和群聊还可以单独覆盖名称或描述。主库保持 **v6**，Room 依赖保持 **2.8.4**。

调研从 `develop@9799b7ed` 开始，实现在 `develop@3aaa963d` 上完成。末尾记录了 SQLite 实验、Android 设备回归用例和验收场景。

## 页面与使用行为

| 入口 | 初始显示 | 用户操作与保存结果 |
|---|---|---|
| 设置 → 用户卡片 | 当前默认人设的头像和名称 | 移除名称下方的二级描述预览。名称本身作为下拉入口，列表勾选默认项，末项为「创建新用户」。选中已有项即更新默认 ID，并切换下方的编辑内容。 |
| 创建新用户 | 仅弹出用户名输入框 | 空白名称不可提交。确认后在同一事务创建并设为默认，描述初始为空、头像使用首字母占位。取消不产生记录。沿用卡片内的改名、描述编辑及头像裁剪入口。 |
| 创建单聊 / 群聊 | 预选打开页面时的默认人设 | 允许改选。开场白预览、宏展开和最终首条消息使用所选人设。可绑定具体人设，也可选择「跟随默认人设」（ID 为 `-1`）。创建时将开场白使用的有效姓名写入 `userName`，描述初始为 `NULL`。 |
| 已有单聊 / 群聊设置 | 当前绑定的人设，分别展示名称、描述覆盖 | 切换只改该会话的 ID，已有覆盖继续生效。输入框显示原始覆盖，继承值作为占位提示。清除一个字段即可让这一项重新跟随人设。单聊沿用字段保存方式，群聊随设置草稿一并保存。 |
| 创建故事 / 故事设置 | 新故事预选「不注入用户人设」，已有故事回显保存的选择 | 复用同一选择器，额外提供「不注入用户人设」。该项写 `-1L`，选择具体人设写其正 ID。故事设置沿用 `expectedRevision` 检查和 `revision` 递增。 |

全局切换默认人设时，只有选择「跟随默认人设」的聊天会继承新的默认资料。编辑人设本身时，绑定它的会话在下次读取时拿到新值，单聊或群聊中已有覆盖的字段继续使用覆盖。重名时按 ID 区分，选择器仅对重名项附加编号。

设置页在头像旁显示名称选择器，卡片内保留名称输入框与描述编辑器。头像裁剪和全屏描述编辑打开时记录目标人设 ID，异步结果按该 ID 回写，避免用户中途切换默认项后改到另一个人设。共享的 Compose 选择器只接收选项、选中 ID 和回调，创建弹窗归设置页，草稿归各页面的 ViewModel。新增文案同步全部现有语言资源，包括法语。[设置页用户卡片](../app/src/main/java/me/kafuuneko/rpclient/feature/main/ui/MainSettingsPage.kt) · [单聊设置](../app/src/main/java/me/kafuuneko/rpclient/feature/chat/ui/ChatSettingsPage.kt) · [群聊设置](../app/src/main/java/me/kafuuneko/rpclient/feature/groupchat/ui/GroupChatSettingsPage.kt) · [故事设置](../app/src/main/java/me/kafuuneko/rpclient/feature/storyeditor/ui/StorySettingsPage.kt)

## Room 数据模型

| 表 | 目标字段 | 约束与用途 |
|---|---|---|
| 新增 `user_personas` | `id: Long`、`name: String`、`description: String`、`avatarFileUuid: String?` | 自增正 ID，名称必填，描述默认空串。头像引用 `files.uuid`，为空时显示占位头像。图片字节继续由文件仓库管理。 |
| 新增 `user_persona_settings` | `id: Int`、`defaultPersonaId: Long` | DAO 只写固定主键 `1` 的单行。默认 ID 外键指向真实人设。创建并启用人设时在一个事务里完成插入和更新。 |
| `chat_sessions`、`group_chat_sessions` | 新增 `userPersonaId: Long`，保留 `userName: String? = null`、`userDescription: String? = null` | ID 非空，正 ID 在写入事务内校验，`-1` 表示跟随当前默认人设。两个覆盖列均允许 SQL NULL。保留原有单聊角色外键和各表索引。 |
| `stories` | `userPersonaId: Long = -1L`，SQL 默认值 `-1` | 物理替换 `includeUserPersona`。持久值只允许 `-1` 或已存在的正 ID。由于 `-1` 没有人设行，故事列由 Repository 在事务内校验，恢复时再做引用校验。 |

设置页的名称输入框右侧始终提供删除按钮。确认后在同一文件仓库事务内解除绑定并删除人设及其头像 UUID。删除默认项时启用最早创建的剩余人设；删除最后一项时创建全新 ID 的 `You`（空描述、无头像）并设为默认。受影响的聊天保留删除前的发言名，改为跟随默认人设；故事切换到不注入并递增修订号。消息、开场白和章节正文保持原文。

在 `AppDatabase` 注册 Entity 和 DAO，在 `RPClientApp` 注册 `UserPersonaRepository`。默认 ID 也由 Room 管理，切换默认只更新单行指针。新头像沿用裁剪与 `FileRepository` 的 UUID/哈希模型，替换时先提交新关联，再释放已脱离的人设专属文件引用。各处引用使用独立 UUID，相同图片共享同一哈希的物理文件。删除旧 UUID 后，由文件仓库检查该哈希剩余的 UUID 引用及读取租约，再决定是否回收物理文件。[主数据库](../app/src/main/java/me/kafuuneko/rpclient/libs/room/AppDatabase.kt) · [依赖注册与启动顺序](../app/src/main/java/me/kafuuneko/rpclient/RPClientApp.kt) · [文件仓库](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/FileRepository.kt)

## 有效人设如何读取

单聊和群聊先按记录里的 ID 取得人设，再逐字段合并。“为空”指 SQL `NULL` 或零长度字符串。新编辑清空时统一写 `NULL`。迁移比较采用原文精确相等，保留有意义的空白、换行和宏。

```kotlin
val effectiveName = session.userName?.takeUnless { it.isEmpty() } ?: persona.name
val effectiveDescription = session.userDescription?.takeUnless { it.isEmpty() } ?: persona.description
```

例如人设「Mira / 档案员」绑定一个仅覆盖名称为「队长」的群聊，实际使用「队长 / 档案员」。之后将人设描述改为「领航员」，该群聊使用「队长 / 领航员」。如果切换到另一个人设，用户仍可清除「队长」以恢复新选人设的姓名。头像始终来自绑定的人设。

- Repository 分别提供原始绑定和解析后的名称、描述、头像。设置编辑使用原始覆盖，显示、生成和导出使用有效值。保存无关设置不能把占位提示或已解析的字段写回覆盖列。
- 单聊、群聊每次生成或每个连续发言批次捕获一次人设快照。开场白、`{{user}}`、`{{persona}}`、世界书匹配、Regex、普通回复、续写、扮演用户、摘要和 Prompt 检查器使用同一作用域。切换默认项不影响正在生成的请求。
- 故事选正 ID 时，创建预览、编辑器、角色宏、续写和摘要均按故事所选人设取值。选 `-1` 时不查询默认人设、不生成 Persona 段，描述传空。需要解析 `{{user}}` 的位置使用中性名称 `DefaultNames.USER`（`You`）。旧实现关闭开关时仍传入全局用户名，这一处行为差异应纳入验收。
- 群聊新用户消息用本轮有效名称写 `speakerNameSnapshot`。已有消息与开场白正文均不重写。群聊历史的显示、摘要和模型上下文统一优先使用消息现存的发言者快照，避免切换人设后把前一位的发言冠上新名字。单聊分支复制原人设绑定和描述覆盖，并保存分支创建时的有效姓名。
- 普通扫描和 FTS 共用的 `SearchProjectionSql.SOURCE_LABEL` 按绑定 ID 或当前默认指针关联人设，等价于 `COALESCE(NULLIF(s.userName, ''), p.name)`。在 `SearchSourceContract` 加入人设名称和单聊绑定 ID 的变更观察，使改名后两个引擎都能刷新标签。无会话上下文的角色列表预览使用 Room 默认人设。

单聊设置保存空名称时清除覆盖。创建、回复、摘要、Regex 和搜索读取对应作用域的人设。故事 Prompt 根据绑定 ID 决定是否注入描述。[群聊 Prompt 构建器](../app/src/main/java/me/kafuuneko/rpclient/libs/groupchat/GroupChatPromptBuilder.kt) · [故事 Prompt 构建器](../app/src/main/java/me/kafuuneko/rpclient/libs/story/StoryPromptBuilder.kt) · [搜索标签 SQL](../app/src/main/java/me/kafuuneko/rpclient/libs/room/dao/search/SearchProjectionSql.kt)

## 在 v6 内迁移已有数据

仓库发布标签 `V2026.4.3` 的主库为 v5。本次沿用开发中的 v6，将提示词预设、Claude 缓存写入统计和人设变更一并纳入 `5 → 6` 迁移。保留 v1 至 v5 的导出结构，更新 `6.json`。请求日志库独立于此次迁移。[v5 结构](../app/schemas/me.kafuuneko.rpclient.libs.room.AppDatabase/5.json) · [v6 结构](../app/schemas/me.kafuuneko.rpclient.libs.room.AppDatabase/6.json) · [Room 迁移与验证](https://developer.android.com/training/data-storage/room/migrating-db-versions)

### 正式版升级的库内变换

- 保留原有 v1 → v5 路径，将现有 `AutoMigration(5, 6)` 替换为显式 `Migration(5, 6)`。在线库与备份暂存库都注册同一迁移。迁移创建提示词预设两表、索引及约束，补充缓存写入统计列并沿用已有统计修正，同时创建人设两表，先插入固定 ID `1` 的迁入占位人设（`You`、空描述、无头像）。暂不写默认指针，其存在将表示跨存储导入已完成。
- 按最终 Room DDL 建新表，显式列出复制字段。两类会话均绑定 `1`，先原样复制旧名称和描述。故事在复制旧行时直接映射 `CASE includeUserPersona WHEN 1 THEN 1 WHEN 0 THEN -1 END`。异常值导致事务失败。完成复制后再移除旧列，避免丢失原开关。仅迁入步骤使用固定 ID，之后所有新会话写实际选中的 ID。
- 三张表都是父表。重建前暂卸应用搜索维护触发器，记录原索引和自增序列高水位。若连接已启用外键，在同一事务用 SQLite 临时表保存受影响的子行，先按子到父顺序移出，再替换三张父表，按父到子顺序回填。范围含 `chat_messages`、群聊成员/消息/摘要，以及故事分卷/章节/角色/世界书关系。尤其要保护章节的 `volumeId` 和摘要的消息边界。外键关闭的迁移连接可直接保留子表原地重建父表。不要依赖在事务中切换 `PRAGMA foreign_keys`。
- 按原 ID 恢复数据、索引和序列高水位（含删过最大 ID 或已清空的表）。核对子表数量、主键与关系，执行 `foreign_key_check`，交给 Room 验证最终结构。正常打开后由现有 `SearchDatabaseCallback` 按原启用状态维护触发器。整段库内变换由事务保护。[SQLite 表重建](https://www.sqlite.org/lang_altertable.html) · [SQLite 外键与级联](https://www.sqlite.org/foreignkeys.html)

### 旧全局设置迁入 Room

旧版身份存在 Kotpref 的 `userName`、`userDescription`、`userAvatar` 三个键中，最后一项是 `files.uuid`。旧创建页使用 `resolvedUserName` 和经过 `trim()` 的描述建立会话快照。应当比较**升级时的用户人设**，无法从旧记录推断更早的全局配置。

- 在 `libs/upgrade` 接入业务升级，打开最终结构后、允许页面或文件清理访问前执行。读取一次旧偏好快照。名称沿用 `normalizedUserName()` 的既有语义，缺失或全空白时使用 `You`。描述缺失时为空，存在时按原文迁入。复用已存在的头像 UUID。空值或不存在的文件索引映射为无头像。若索引存在但字节暂缺，保留 UUID，界面可显示占位。
- 在一个 Room 事务里填充迁入人设，分别处理两类会话，然后写入单行默认指针。对全新安装，建首条 `You` 人设和默认指针即可。已有有效默认指针说明初始化已提交，重试直接复用，不能覆盖用户后续改名或重新选择的默认项。遇到已有多人设但缺少有效默认指针的异常数据，走恢复校验，不把它当空库重新导入。
- 旧会话固定历史姓名；原姓名为空时使用迁入的人设名称。描述仍独立比较。假设迁入的人设为「Mira / 档案员」，下表也适用于群聊。比较不改大小写、不展开宏、不裁剪旧文本。若历史创建时曾裁剪描述而当前偏好保留了空白，保留有差异的旧会话原文。

| 旧名称 | 旧描述 | 迁移后的名称覆盖 | 迁移后的描述覆盖 |
|---|---|---|---|
| Mira | 档案员 | Mira | `NULL` |
| 队长 | 档案员 | 队长 | `NULL` |
| Mira | 领航员 | Mira | 领航员 |
| 队长 | 领航员 | 队长 | 领航员 |
| Mira | 空串 | Mira | 保留旧空串。按新的空值读取规则，实际描述继承「档案员」。 |

可用绑定参数在两张表分别执行以下变换。对 `group_chat_sessions` 使用相同语句，仅替换固定表名。

```sql
UPDATE chat_sessions
SET userName        = COALESCE(NULLIF(userName, ''), :legacyPersonaName),
    userDescription = NULLIF(userDescription, :legacyPersonaDescription)
WHERE userPersonaId = :importedPersonaId;
```

人设迁入由 `AppUpgradeManager` 注册的 `Upgrade20260404` 调度，与本版本提示词预设迁移共用一个版本步骤，应用 versionCode 保持 `20260404`，Room 结构仍为 v6。`migrate()` 打开已完成结构升级的数据库，读取旧偏好并提交人设；Room 默认指针作为库内幂等标记，保留已迁入、已编辑或由备份恢复的人设。Manager 在迁移返回后记录迁移检查点，全部版本迁移成功后才调用 `cleanup()` 同步删除三个旧键并记录清理检查点。数据库提交后检查点写入失败、后续迁移失败或清理失败均可安全续跑。备份恢复继续使用 `UserPersonaUpgrade.migrate()` 和归档自己的偏好，不修改在线升级检查点。

## 完整备份与单项导入导出

完整备份有自己的 v3 格式。人设两表可由通用表导出，头像走现有 `files` 与附件目录。但单聊和故事走专用编解码，通用格式使用有效名称和描述，完整备份额外保存原始继承状态与绑定。[完整备份格式](manual-backup-restore.md) · [v3 专用读写器](../app/src/main/java/me/kafuuneko/rpclient/libs/backup/PortableBackupV3.kt)

| 场景 | 导出和导入规则 |
|---|---|
| 单聊菜单 JSONL | 继续向酒馆格式写有效名称和描述。导入确认时预选本机默认人设，固定归档中的发言名，缺失时保存所选人设的名称。描述相同或为空时继承。解码保留字段是否实际存在，避免把读取器的备用用户名当作显式覆盖。 |
| 故事菜单归档 | 保持现有 v1/v2 可读，v2 的传输字段 `includeUserPersona` 从 ID 推导。可选的人设名称提示用于导入确认，不导出本地 ID。旧归档为 `false` 或缺省时选 `-1`，为 `true` 时预选本机默认项。新归档可按唯一提示预选，人名相同或未匹配时由用户在确认页选择。纯文本导入沿用 `-1`。布尔值只存在于兼容格式。 |
| 完整备份 v3 | 在 `rpclient_backup.session` 保存来源人设 ID 及两个独立的覆盖状态（继承 NULL、旧空串、使用归档正文的覆盖），在故事的本地附加信息保存来源人设 ID。菜单格式继续展示有效值，恢复依附加信息还原真实绑定与原始可空列。群聊 JSONL 直接保存数据库行。读写均区分 JSON null、空串及缺键，避免 `optString` 产生字面量 `"null"`。 |
| 完整恢复 | 按来源结构读取归档，保留人设原始正 ID、默认指针和三类绑定，三类记录的 `-1` 均原样恢复。新版归档出现缺失或歧义人设引用时，在通用外键裁剪之前报告错误并保留在线数据，避免为处理丢失人设而删掉整段聊天。无本地附加信息的新增文档按菜单导入规则处理，所用默认项取自归档。 |

旧 v3、portable v2、V1 JSONL 和原始 SQLite 快照仍按现有恢复入口处理。重建旧结构时先保留旧会话快照和故事布尔值，再进入统一的结构迁移。暂存库必须只从**归档自己的** `shared-prefs` 读取旧人设。缺键采用旧应用默认值。已含人设库、默认指针和有效引用的备份直接恢复，不能被本机偏好或旧检查点覆盖。将人设迁入与已有 `PromptPresetRestore` 一起接入 `BackupDatabaseValidator.preparePrimaryForRestore`，各自只处理自己的键。最后校验默认项、头像索引、三类记录的正 ID 与各自的 `-1` 语义，通过后才提交替换。[暂存库验证入口](../app/src/main/java/me/kafuuneko/rpclient/libs/backup/BackupDatabaseValidator.kt) · [单聊归档](../app/src/main/java/me/kafuuneko/rpclient/libs/chat/ChatArchiveRepository.kt) · [故事归档](RPClient-Story归档格式.md)

## 已验证与待验收

调研中用仓库导出的正式版 v5 建立 SQLite 3.54.0 内存库，在外键开启和关闭时执行三表重建和逐字段迁入。样本核对了五种覆盖组合、头像 UUID、故事开关两种取值、八张子表的完整行、消息图片关联、自增序列高水位和 `foreign_key_check`。迁入后改名再重跑，保留了新名称。Android 设备测试覆盖正式版跨版本迁移，以及保留两套人设、三类绑定、NULL、旧空串和显式覆盖的备份往返。

从首页分别创建单聊、群聊和故事，保留全局默认人设并在创建页改选另一人设。保存后逐表核对，三条记录均绑定所选人设，当时两种聊天的名称和描述均为 `NULL`；现行规则已改为创建时固定发言名。另在创建人设的弹窗用快速连续按键输入姓名，六轮均保留完整文本。[输入回显回归](../app/src/androidTest/java/me/kafuuneko/rpclient/ui/widgets/BoundTextFieldStateTest.kt)

移除开发版兼容前的完整回归中，403 项单元测试全部通过。Android 16 的 221 项设备用例中，218 项通过，按项目配置跳过两项性能基准和一项外部终止进程测试。Android 17 上有三个 JSON 查看器用例未找到系统复制菜单，在未修改的 `develop@3aaa963d` 上单独复跑也得到相同结果。

移除旧开发库转换后，重新构建 Debug APK 和设备测试 APK，403 项单元测试全部通过。Android 16 上定向运行正式版结构迁移、人设迁入、完整备份恢复、归档偏好恢复和设置页创建切换共 34 项设备用例，全部通过。修改的五份 Kotlin 源码通过项目原生格式化及只读检查。

本次删除功能在 Android 16 隔离模拟器上通过 49 项定向用例，覆盖删除最后一项后重建 `You`、三类绑定、姓名保留、正式版迁移、归档往返和搜索。两个设置页的界面用例在输入框未聚焦时直接检查继承姓名和描述。
