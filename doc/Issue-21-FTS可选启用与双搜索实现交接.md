- FTS 改为用户主动选择开启；默认关闭，普通搜索仍然可用。用户确认开启后，全量构建已有数据，完成后才启用 FTS 搜索。

- **用户最终明确不需要给所有 Repository 加全局锁。** Loading 管交互，索引管理器串行管理构建／取消／清理，日常增量通过现有事务与修订号保证一致性。
- **用户最终明确不增加修订号溢出专项处理。** 保留 Long，关闭时清掉 FTS 自己的版本与进度，再开启时重建并重新初始化。

## 用户已确认的行为

### 开启与首次全量构建

- 用户自行决定是否开启，不能默认在升级或启动后替所有用户建索引。
- 点击开启后需要用户确认，再展示构建 Loading；不能先把开关标成已开启再异步慢慢建。
- 全量处理已有的普通单聊消息、群聊消息和全部故事章节，不截短历史范围。
- 构建期间用户不能继续其他界面操作，Loading 提供明确取消入口。
- 构建完整成功后才进入已开启状态，后续搜索使用 FTS。

Loading 建议提供已处理数量等真实进度，不在未知总量时伪造百分比或固定完成时间。长操作在后台执行，UI 保持响应，以便用户取消。

### 取消与关闭

- 用户取消构建后，清理已经生成的 FTS 相关数据，最终保持关闭。
- 用户关闭已开启的 FTS，也要清理派生数据以腾出空间；仅停止工作器不满足要求。
- 清理应包含正文块、倒排数据、源状态／修订号／待办、全局搜索版本和补建进度。允许保留必要的轻量开关／清理状态，原始业务正文与其他业务记录保持完整。
- 关闭再开启时，从业务原文重新完整构建，FTS 修订号和进度重新初始化。
- 清理完成前要阻止旧任务继续写回；重复点击和快速开关不能产生重叠构建或清理。

### 开启后的日常更新

- 新增、编辑、删除消息或章节后，继续进行小批后台索引更新。
- 用户可以正常发送、编辑、删除；不为每批更新弹 Loading，不因整段文字处理长期锁住业务操作。
- 保留业务变更与持久待办一致提交的约束；如果从触发器改为 Repository 登记，也不能改成提交后仅发一次内存通知。
- 保留单工作器、源修订核对、最后一批完成后才发布，以及删除／脏源旧结果排除。
- Loading 只限制用户交互，已存在的生成、自动保存等后台任务可能继续运行，靠事务与修订号处理它们，并把构建期间产生的待办计入完成判定。

### 并发设计的最终边界

用户否定了前面讨论中过度扩大的全局业务锁方案。**不要给 ChatRepository、GroupChatRepository、StoryRepository 等统一增加一把覆盖全体业务的互斥锁或全局维护门禁。**

保留或收敛索引管理器自己的生命周期互斥，协调开启、构建、取消、关闭和清理。不要在持有同一个非重入 Mutex 时再次调用会获取该锁的公共方法，也不要持锁等待一个必须获取同锁才能退出的任务。

取消／关闭的逻辑顺序应保证：阻止新索引任务启动、使旧查询失效；取消并等待旧任务退出；停用索引业务维护入口并安全清理；持久化清理完成状态，再恢复普通搜索交互。具体事务边界由实现决定，但不能出现清理完成后旧工作器重新写入的情况。

### 修订号溢出

- 保留当前 Long 修订号与请求代次设计。
- 用户理解正常使用不会耗尽 64 位计数范围，明确决定不增加专门保护。
- 不增加 Long.MAX_VALUE 阈值处理、溢出恢复状态机，也不为了这个问题更换 UUID／BigInteger 等方案。
- 关闭必须清除 FTS 自己的修订及进度，因此即使被人为改成异常上限，完整关闭后重新开启也能重新初始化。
- 重置范围仅限搜索派生状态，不能重置故事等业务自己的修订号；清理不能依赖“异常修订号恰好匹配”才允许删除。

## 建议的实现结构

以下名称用于说明职责，可按项目命名习惯调整；“共同接口＋两个实现”的划分来自用户要求。

| 角色 | 建议名称 | 职责 |
| --- | --- | --- |
| 搜索接口 | ContentSearchEngine | 统一查询、分页、取消与部分结果契约 |
| FTS 实现 | FtsSearchEngine | 使用现有 FTS4 索引查询 |
| 普通实现 | DatabaseScanSearchEngine | 分批读取业务原文并匹配，不依赖 FTS 数据存在 |
| 搜索统一入口 | 现有 Repository 或小范围路由层 | 根据有效模式选择实现，共用结果模型与必要的元数据逻辑 |
| 开关与索引管理 | SearchIndexManager 或重构现有索引仓库 | 管理模式、构建进度、生命周期、清理与日常增量 |

页面通过 MVI 接收状态、发 Intent，不在 Compose 里读偏好、操作数据库或选择实现。开关和管理状态由业务层持有，不能只存在某个对话框的 remember 状态中。

FTS 已成功开启且索引可用时才选择 FTS 实现；关闭时选择普通实现。构建／清理期间由 Loading 限制界面交互，不把半成品索引当作已开启搜索。模式切换应取消旧查询并作废旧分页，避免旧任务回写、混用结果。

### 普通搜索需要真正解除 FTS 依赖

现有 `ContentSearchQueryRepository.search()` 在判断 `request.directScan` 前就读取 `search_progress`，并调用 `first { kind == 0 }`；`directPage()` 结束时也读取该版本。直接清空进度后复用当前代码会失败。

接手时需要：

- 将普通搜索从 FTS 就绪状态、补建游标和 FTS 全局版本中解耦。
- 单独设计普通搜索的分页与变更处理；开关切换后不能继续使用旧模式游标，导航前归属校验继续保留。
- 保持范围、对象去重、排序、片段、取消、部分结果与完整性表达；不要为提速固定截取前若干条历史。
- 共用文字投影和规范化，尽量保持两种实现搜索语义一致。
- 在 FTS 记录清空、重启应用、业务继续增删改后，都验证普通搜索可用且不会悄悄创建 FTS 待办。

用户提出“数据库内简单的耗时匹配”。具体可复用现有分批原文扫描。直接对原始 Markdown 使用 LIKE 会改变匹配行为，例如 `你**好**` 原文不能被 `%你好%` 命中；think 排除、大小写与 Unicode 规范化也需要保持。共享可见文字处理是延续现有语义的实现建议，不应无说明地缩小匹配范围。

## 建议的状态与异常恢复

以下四态是前一个 AI 给出的落地建议，用户没有规定类型名或持久化位置；实现可以等价调整。

| 状态 | 用户界面 | 后台与持久化要求 |
| --- | --- | --- |
| Disabled | 普通搜索可用 | 不启动 FTS 工作器，不积累专用待办，正常情况下无旧索引内容 |
| Building | 构建 Loading，可取消 | 保存未完成阶段，只有全量登记和全部待办完成后才切换为 Enabled |
| Enabled | 正常使用 FTS | 启动日常增量维护，修改中源不返回过期正文结果 |
| Cleaning | 正在停止／清理 Loading | 阻止新的 FTS 任务，等待旧任务退出，完成清理后进入 Disabled |

持久化可以使用现有轻量偏好或合适的管理状态，不要求新框架。如果偏好与数据库分开保存，需要设计跨存储中断恢复顺序，不能假设它们自动组成同一个事务。

若接手时存在旧自动构建实现留下的索引，且没有用户明确开启的新状态，应按默认关闭路径停用维护并清理遗留派生数据；不能仅因旧索引存在就视为用户已经确认开启。仍须遵守当前未发布 v5 开发库的结构兼容边界。

建议的异常策略：

- 构建失败：保持 FTS 未开启，进入清理并反馈失败；不要发布“已开启”。
- 构建期间杀进程：下次进入后识别未完成状态，先清理，再保持关闭；不静默继续昂贵全量构建。此为前一个 AI 的推荐恢复策略，落实时应与可取消构建的一致性一起验证。
- 清理期间杀进程或清理失败：保留未完成清理状态，可在下次进入时幂等续清理，不能误判已完成或再次启动构建。
- 已开启后正常重启：恢复原有可用索引和持久增量待办，不每次启动都清空全量重建。
- 未来格式变化或索引不可用：不能沿用当前后台静默全量补建而绕过新的交互约定；全量重建、重试与回退普通搜索应统一经过管理器。具体提示策略可在实现时完善。

返回键、外部点击、旋转和 Activity 重建需要统一处理：返回若用于取消，必须走取消清理；外部点击不能只让对话框消失。旋转或重新进入时应从管理状态恢复 Loading。不要承诺应用在后台或被强杀后仍持续构建。

### 触发器与关闭状态

当前回调在三张正文表安装九个源触发器，在六张元数据表安装十八个失效触发器。关闭后需要使搜索专用维护停止，避免用户普通保存仍不断生成 FTS 状态。

不能只暂停工作器，也不能只在当前进程删触发器而让 `onOpen()` 下次重新无条件安装。应将安装、停用、进度初始化和状态恢复作为同一套管理规则。采用 `CREATE TRIGGER IF NOT EXISTS` 时，还要考虑用户库里旧定义不会自动替换的问题。

现有 FTS4 为 Room 外部内容表，还有四个 Room 管理的内容同步触发器。清理需使用与 FTS4／Room 相容的正确流程，确认倒排内部数据也被清理；不能只删 `search_sources`，也不要套用 FTS5 专用命令。

### 空间回收要求

用户要求“关闭后清理记录、腾出数据库空间”。验收要同时检查逻辑数据和实际文件占用。

- 若继续沿用主库，可保留 Room 声明的空表结构，清理派生内容；不能随意删除 Entity 对应的表而破坏下次打开时的结构校验。
- 同时考虑 FTS 内部数据、主库空闲页、WAL 与 SHM。记录数归零不能单独证明已经把空间还给文件系统。
- 先核对实际数据库 auto_vacuum 与设备表现，再决定回收措施；全库 VACUUM 会带来额外时间与临时空间要求，不宜无条件执行。
- 所有清理步骤需要幂等，任务取消或进程中断后可恢复；清理业务原文不属于此功能的允许范围。
- 独立索引数据库仅作为进一步降低故障耦合、简化文件空间回收的候选，**用户尚未决定分库，不应把它当作已确认要求**。

参考机制：[SQLite 空间回收](https://www.sqlite.org/lang_vacuum.html)、[WAL 与 checkpoint](https://www.sqlite.org/wal.html)。若选择分库，应先明确其额外跨库一致性成本和实施范围。

## 需要继续保留的现有体验

- 首页以按钮进入独立搜索页，完整历史消息和全部章节正文保持可检索。
- 分类、标题／角色与正文范围、对象内搜索、取消、部分结果、分页和导航前复核归属继续保留。
- 单聊／群聊历史定位、双向加载及全历史 Display Regex depth 保持正确；最新消息已经加载时不再显示多余返回按钮，手动到底后恢复跟随。
- 故事按稳定章节 ID 打开，可靠时定位原文，无法可靠映射时保守打开章节。
- 三种创建页的角色筛选仍独立于正文 FTS；按钮和输入框继续遵循透明度、模糊度与本地化规范。

## 版本、数据与范围约束

- **Room version 保持 5。** 用户此前明确此版本未发布，允许破坏性修改未发布结构；如改 Entity，应更新导出 schema 并维持已发布旧版本的迁移链。

### 新流程必须验证

| 场景 | 验收要点 |
| --- | --- |

| 关闭已启用 FTS | 搜索切回普通实现；清理索引、修订及进度，验证实际空间减少 |
| 关闭后继续增删改并重启 | 普通搜索反映当前原文；不重新安装并启用专用维护，不重新生成 FTS 数据 |
| 再次开启 | 从当前原文完整重建，重新初始化搜索修订与进度，不混入旧内容 |
| 构建或清理期间杀进程 | 根据持久阶段恢复，不能把半成品当成已启用或把未完成清理当完成 |
| 已启用后的日常更新 | 用户可正常操作；编辑、删除、同 ID 重插不返回过期索引；待办最终完成 |
| 两种实现的结果与分页 | 中英文、符号、Markdown、think 排除、跨块、对象去重与导航一致；切换后旧游标失效 |
| 布局与语言 | Loading、确认、取消、失败文案本地化；小屏、大字体和外观样式可用 |

不需要为了溢出本身新建专项用例；关闭／重开的测试需要确认 FTS 派生版本确实重新初始化。重点做真实数据库的流程与一致性回归，不写仅验证接口转发或属性赋值的测试。
