- 开始一个阶段时，立即更新“当前进度”和阶段总表，将该阶段设为“进行中”。
- 每完成一个具体任务，核实对应产物后勾选；尚未实现、仅有接口草图或仅写出测试的任务不得勾选。
- **每个阶段结束后，必须先更新本文件，再进入下一阶段。** 同步更新该阶段任务项、阶段状态、完成阶段数、最近更新日期和执行记录。
- 执行记录必须包含实际改动、文件或提交依据、验证命令及结果、遗留问题和下一步。不得用“已检查”“应该可用”代替验证结果。
- 代码完成但验证未做或未通过时，阶段标为“待验证”，不计入已完成阶段；遇到依赖或环境阻塞时记录原因、影响范围及恢复条件。

- 后续改动破坏已完成阶段的验收条件时，重新打开对应任务和阶段，记录原因，并修正完成阶段数。
- 调整实现细节时同步记录理由；出现需要改变用户已确认行为的新决策，按用户要求暂停相关工作并询问，不擅自替换既定方案。
- 本期全部阶段通过验收、未解决问题清零并完成最终记录后，才将总状态改为“已完成”。“代码已完成但缺真机／协议验证”不能写成“功能已全部完成”。

## 固定范围与约束

后续每个阶段都必须满足下列约束：

- 保持 `ChatMessage`、`GroupChatMessage` 两张表结构不变，新增 `message_images` 记录 `messageId`、`messageType`、`imageUuid`、`position`。
- 保持 `AppDatabase.version = 4`，不新增 `4→5`；在未发布的 `4` 内维护最终 schema，保留既有历史 schema 与迁移链。
- 原图通过 `FileRepository` 保存；相同字节共享物理 hash 文件，各附件持有独立 UUID。原图与可重建缓存分开管理。
- 支持单聊、群聊的用户纯图片消息与文字附图消息；本期不支持模型输出图片或任意正文段落间插图。
- 使用有序文本／图片内容块，接入现有三种协议，流式与非流式共用准备与校验逻辑。
- 图片随所属历史消息参与请求，正文和附件一起裁剪；当前用户提交的图文不能被静默裁掉。
- 摘要直接读取图片，成功后保存文字摘要，原图继续保留；摘要模型独立检查视觉能力。
- 明确不支持图片的模型拦截含图请求，未知能力允许尝试；不得自动忽略图片或偷偷切换模型。
- 请求日志不保存图片 Base64；图片缺失、导出遗漏或请求超限必须明确反馈。
- 遵循 `coding-guidelines.md` 及现有 Feature、MVI、Repository、Koin 分层；按规范补充中文 KDoc、必要行内注释与有价值的验证，不做无关框架重写。

客户端限制沿用调研建议初值：每条消息最多 `4` 张、每次请求最多 `12` 张；原图单张 `32 MiB`／`48` 百万像素；默认发送长边 `1536 px`、发送文件 `2 MiB`、完整 HTTP JSON `16 MiB`。这些数值需集中定义，并在真机和网关验证后记录调整依据，不视为服务商统一保证。

本期必须完成文字 JSONL 导出的图片遗漏提示。完整携图归档包、服务商 Files API 缓存、更丰富的质量选项等继续列为后续扩展，不借此缩减已确认的图片发送、历史与视觉摘要能力。

## MEDIA：图片处理、缓存与资源限制
