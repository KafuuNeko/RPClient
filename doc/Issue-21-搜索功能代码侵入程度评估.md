# Issue #21 搜索功能代码侵入程度评估

> 审计日期：2026-10-19。基线为 `f8d074b`，目标为当前合并提交 `f7538de`。范围包含角色筛选、独立全文搜索、索引存储优化、历史定位与最新按钮修复。本次仅调研与记录，不修改生产代码。

## 结论

**总体代码侵入程度为中等，数据库运行时耦合偏高，页面与框架层的侵入较低。**

搜索页面、编码、查询、索引维护基本集中在新增文件，原有业务实体结构保持不变；但功能已接入主数据库的打开、写入与空间维护，也改变了单聊和群聊的窗口及滚动状态。因此不能把它视为只增加一个独立页面的功能。

优先需要管理的影响是：搜索派生数据与原文共用主库、触发器随业务事务执行、历史窗口状态与聊天跟随逻辑交织。当前没有静态证据要求整体重写；应先补足故障隔离与混合负载验证，再决定是否拆分存储。

### 数据库：代码改动少，但执行路径覆盖广

[数据库声明](../app/src/main/java/me/kafuuneko/rpclient/libs/room/AppDatabase.kt)与两份 `5.json` 对比显示：新增 `search_sources`、`search_chunks`、`search_progress` 三张普通表和 `search_chunks_fts` 虚拟表；既有 Entity 定义未变，没有因本次搜索增加消息正文、角色或故事业务字段。

[SearchDatabaseCallback](../app/src/main/java/me/kafuuneko/rpclient/libs/search/SearchDatabaseCallback.kt)安装的业务触发器包括：

- 三张正文源表 `chat_messages`、`group_chat_messages`、`story_chapters`，每张分别处理插入、相关字段更新、删除，共九个触发器。
- 会话、故事、角色及成员关联等六张元数据表，每张三个事件，共十八个触发器。
- 上述合计二十七个；Room 另外为 FTS 外部内容表维护四个同步触发器，不包含在前述数量内。

触发器使批量导入、普通保存、修改和级联删除自动登记搜索待办，减少逐个改写业务保存入口的需要。这也形成数据库层的隐式依赖：业务 DAO 不调用搜索仓库，写入仍然会执行搜索 SQL。

正文源触发器在同一业务事务内执行 `INSERT OR IGNORE search_sources`、更新源修订以及递增 `search_progress`。后台构建的异常与这部分同步执行必须区分：

| 故障位置 | 当前边界 |
| --- | --- |
| 后台 Markdown 投影、token 编码、FTS 写入或查询失败 | 可进入不可用状态，提供元数据查询或主动原文扫描；原文保存不以后台索引完成为前提 |
| 主库打开回调中的建触发器、初始化进度失败 | 可能影响主库打开，覆盖面超出搜索页 |
| 业务触发器 SQL、搜索状态表写入失败 | 可能使当前业务写入事务失败；后台工作器的异常捕获不能隔离此路径 |
| 同一主库的磁盘耗尽、文件损坏或写锁竞争 | 索引与业务共同承受，低空间检查不能提供完整隔离 |

这里描述的是结构上的故障传播路径，并非已经复现了触发器故障。也不能把仅有的 FTS 查询失败等同于所有业务事务都会失败。

[索引工作器](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/ContentSearchRepository.kt)已用短批事务、代次确认、变更合并和约 65 MiB 可用空间保护降低争用。后台协程解决了执行线程问题，但数据库写事务、I/O、CPU 和存储预算仍与聊天、故事保存共享。

### 聊天与群聊：最主要的业务代码侵入点

[ChatRepository](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/ChatRepository.kt)和[GroupChatRepository](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/GroupChatRepository.kt)的原有页面读取接口增加可选锚点与两侧窗口参数；原来的调用方式仍可使用默认参数进入最新窗口。新增能力围绕稳定消息 ID 和创建时间，不要求聊天仓库依赖搜索索引表或查询仓库。

[单聊 ViewModel](../app/src/main/java/me/kafuuneko/rpclient/feature/chat/ChatViewModel.kt)、[群聊 ViewModel](../app/src/main/java/me/kafuuneko/rpclient/feature/groupchat/GroupChatViewModel.kt)与对应 Layout 增加了这些状态和约束：

- 保存锚点与尚未加载的较新消息数，向两端分页时维持真实全历史 Display Regex depth。
- 历史阅读时关闭底部跟随；主动生成或返回最新窗口时恢复跟随。
- 当前消息窗口刷新时保留锚点两侧数量，处理命中被删除或归属改变。
- 最新消息已经加载且用户滚到底时退出历史定位，保留现有消息窗口。
- 两类 Layout 都新增布局完成判断，并在尺寸变化滚动前等待下一帧，普通聊天的键盘与尺寸变化路径也需要回归。

这些调整是“全文命中能够真正打开历史位置”的必要配套。维护复杂度集中在分页、刷新、生成与视口状态的交叉处，不在搜索按钮本身。

目前两套 ViewModel 与 Layout 存在相似的锚点和分页控制；后续修改一端容易遗漏另一端。可考虑提取小范围的历史窗口状态与共同规则，继续由各页面持有自己的列表、输入和生成状态。

锚点前后读取的正文数量有界，但新增的 `countAfter()` 仍要统计目标之后的记录范围。远距离历史定位的成本不能仅由单页消息数推断为常数，需要单独测量极大单会话的定位时间。

### 故事编辑器：局部状态扩展

[故事初始化](../app/src/main/java/me/kafuuneko/rpclient/feature/storyeditor/StoryEditorViewModel.kt)复用原本就支持指定章节的 `StoryRepository.getStoryEditorData()`，本次没有修改 StoryRepository。

新增 `StoryEditorDocument.searchRange` 及对应选择、首次滚动、高亮逻辑。普通入口没有查询时，范围映射很快返回空值；原有保存、撤销、续写与冲突处理实现未被搜索代码改写。

耦合点是编辑器直接依赖 `SearchTextCodec.literalRange()`，而该 Codec 同时承担规范化、索引编码和 Markdown 投影。当前依赖方向仍符合 feature 调用工具层的分层；若文本定位后续扩展，可再拆出范围映射职责。

### 首页、创建页与公共组件：以局部接入为主

首页只增加搜索入口和分类参数传递，查询、结果和慢任务在独立 `feature/contentsearch` 中维护。

三种创建页共用 [CharacterSearchField](../app/src/main/java/me/kafuuneko/rpclient/ui/widgets/CharacterSearchField.kt) 和 [matchesCharacterQuery](../app/src/main/java/me/kafuuneko/rpclient/utils/CharacterSearch.kt)，按名称、描述和标签进行内存筛选。它们不依赖正文 FTS；索引是否就绪不会决定创建页角色筛选是否可用。后台结果回写使用最新列表保留选择状态。

搜索页复用已有 `PageButton`、`PageFilterChip`、`PageOutlinedTextField` 和背景装饰。最近的按钮透明度与模糊修复只调整搜索页引用，`PageButtons.kt` 本身在本次差异中没有修改。因此不会通过修改全局按钮实现改变其他页面样式。

## 长期维护与撤回成本

### 业务结构变化需要同步搜索契约

[SearchSql](../app/src/main/java/me/kafuuneko/rpclient/libs/search/SearchSql.kt)、[SearchSourceReader](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/SearchSourceReader.kt)、触发器及正文查询直接使用业务表名、字段名、类型编码和 `Summary` 枚举存储值。部分组合查询走 `RawQuery`，编译期保护弱于固定 `@Query`。

未来变更消息来源枚举、章节字段、角色关联或排序时间，需要同步检查投影、触发条件、元数据查询、重建和导航归属。现阶段三类源规模适中，集中维护这份契约与集成回归，比立即引入多层适配框架更合适。

### 触发器更新与正文格式更新是两件事

触发器采用 `CREATE TRIGGER IF NOT EXISTS`。这可以重复打开数据库，但未来仅修改 Kotlin 中的触发器 SQL，不能替换用户数据库里已经存在的同名触发器。

`SearchTextCodec.FORMAT_VERSION` 只负责让源和正文投影重新处理；它不会自动更新触发器定义。发布后变更触发器时，需要通过可重复执行的数据库迁移或版本化安装逻辑更新旧定义，并验证旧库升级。

元数据触发器目前监听全部 UPDATE 字段，例如与搜索无关的角色字段更新也可能使搜索分页代次失效。可以按实际查询依赖缩小更新字段集合，但要一起处理已安装触发器的升级。

### 隐藏入口不等于撤回索引能力

仅移除首页入口不会停止应用级工作器；仅停止工作器也不会移除业务触发器或释放索引占用。若只是暂停后台处理，新的业务变更仍会累计持久待办。

如果将来正式移除功能，需要统一处理启动注册、主库回调、业务触发器、FTS 同步结构、派生表及页面锚点契约。移除业务触发器必须先于移除其引用的表。涉及真实用户库时应通过受支持的版本迁移执行。

本次按既定要求保留 Room version 5，旧业务 Entity 没有变化；旧的未发布 v5 开发库仍存在 schema 哈希差异，不能当作已发布版本之间的兼容承诺。发布后的结构变更需要正常版本迁移。

### 分库的收益与代价

若产品要求“索引文件损坏时聊天保存仍可用”，独立索引数据库值得专项评估。它可以隔离索引文件及部分写锁争用，但会带来跨库源修订同步、可靠待办、结果归属校验和元数据关联设计；同一设备磁盘耗尽仍是共同风险。

若可靠待办继续留在主库，业务事务与待办的小范围耦合依然存在；若完全移除持久待办，又要解决进程中断后的变更漏记。当前直接跨业务表的查询也需要调整。因此分库是较大设计改动，应由可用性要求和实际混合负载结果驱动。

## 已有证据与验证缺口

已有证据引用本任务此前的执行结果；本次审计没有重新运行构建、压测或故障注入。

| 已有证据 | 能支持的结论 | 不能据此推出的结论 |
| --- | --- | --- |
| 309 项 JVM 测试与 21 项实机回归 | 编码、分页、脏数据排除、删除、重插、恢复等已有回归 | 所有原有业务组合都已覆盖 |
| 后续三项模拟器界面回归 | 首页到搜索、单聊与群聊定位、末尾状态和按钮居中 | 实机所有键盘、主题和后台恢复组合都稳定 |
| 100 MiB／500 MiB 合成库基准 | 当前语料的索引占用、独立搜索耗时及部分规模边界 | 启用搜索前后聊天保存性能没有变化 |
| 当前 schema 对比与旧库迁移测试 | 既有 Entity 未变，已有迁移测试校验目标结构和部分旧数据 | 已完整覆盖旧消息／故事库升级后补建中断再重开的链路 |

尤其需要注意：[基准测试](../app/src/androidTest/java/me/kafuuneko/rpclient/libs/search/ContentSearchBenchmarkTest.kt)在索引 Ready 后调用 `index.stop()`，再测量搜索。它测量的是完整查询链路，但没有同时施加后台建索引与前台编辑保存压力。此前“原实现”对照也已经含有搜索，不能作为“尚未接入搜索”的写入性能基线。

建议优先验证的边界：

- 同一业务语料下，无搜索基线与启用搜索的保存、批量导入、故事自动保存延迟对照；同时记录 P95、主库／WAL 峰值和前台卡顿。
- 主库真实文件上的补建中途终止进程并重开，确认待办、半成品、旧内容与删除内容均正确；现有内存库 stop/start 回归不能替代此验证。
- 由 v4 旧库开始，保留大量历史单聊、群聊和故事，经升级、补建和再次打开后验证可检索性。
- 搜索触发器或派生结构异常时的打开、业务保存与恢复行为，以及磁盘低空间保护的实际边界。
- 超大单会话的远距离定位及生成期间滚动、设置返回、键盘尺寸变化；最低 API 26 需另行验证。

## 后续优化建议

| 优先级 | 建议 | 目标 | 建议范围 |
| --- | --- | --- | --- |
| 高 | 补业务写入混合负载及文件库中断／升级回归 | 量化对原有可用性的影响，验证持久恢复 | 测试与观测优先 |
| 高 | 明确触发器的升级与故障边界 | 防止发布后规则更新只对新库生效，避免错误宣称完全隔离 | 数据库安装与迁移设计 |
| 中 | 收敛单聊／群聊历史窗口共同行为 | 降低双份状态逻辑漂移，保留各页职责 | 小范围提取与针对性回归 |
| 中 | 审查 SQL 业务契约及元数据 UPDATE 字段 | 降低结构变更遗漏与不必要的游标失效 | 搜索层内部整理 |
| 条件性 | 评估独立索引数据库 | 强化索引故障隔离 | 在明确隔离目标或实测争用超标后专项设计 |

当前适合保持现有 Feature／Repository 分层，优先处理上述验证和生命周期契约。若后续需要继续降体积，见[存储优化实机记录](./Issue-21-搜索存储优化实施与实机验证.md)；其中约 100 MiB 原文对应 347.44 MiB 稳态主库的结果也说明，同库搜索的资源影响需要作为业务体验的一部分持续评估。
