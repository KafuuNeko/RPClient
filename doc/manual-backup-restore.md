# 完整数据备份与恢复

在 **设置 → 数据与系统 → 备份与恢复** 中可导出 `RPClient-Portable-Data.zip`。

## 归档结构（v3）

```text
RPClient-Portable-Data.zip
├── manifest.json                  格式与版本，不含校验和
├── characters/<名称>-<id>.json     Character Card V2（内嵌绑定的世界书、角色正则与本地备份扩展）
├── worldbooks/<名称>-<id>.json     酒馆世界书（含角色绑定的世界书）
├── regex/global-scripts.json       仅全局正则脚本数组
├── stories/<标题>-<id>.rpstory.json
├── chats/<标题>-<id>.jsonl         酒馆 JSONL
├── group-chats/<标题>-<id>.jsonl   每行一个数据库行（无菜单导入器）
├── tables/<表名>.jsonl             其余业务表，每行一个数据库行
├── request-logs/<表名>.jsonl       请求日志库
├── attachments/<sha256>            附件，保持原始二进制
├── shared-prefs/*.xml              偏好，保持原始 XML（保留类型）
├── private-files/                  应用私有文件
└── app-data/
    ├── database-schema.json        技术结构，不要手改
    └── request-log-schema.json
```

### 单一事实来源

- 角色、世界书、正则、故事、聊天文件使用各菜单导入所用的格式，文件内容就是恢复时读取的内容；每个文件都能在对应菜单单独导入。
- 这些格式无法表达的列（数据库主键、头像文件 ID、额外主开场白、世界书条目分类、故事章节修订号等）放在文件顶层的 `rpclient_backup` 键下。各菜单的导入解码器会忽略该键。格式内已有的字段不会在该键里重复保存，所以改正文只需要改一处。
- 没有菜单导入器的表使用每行一个 JSON 对象的 JSONL，行内容就是数据库行。
- 搜索加速属于可重建的派生数据，不导出 `search_sources`、`search_chunks`、`search_progress`、FTS 虚表数据或影子存储；运行期搜索维护触发器也不写入归档。技术 schema 仅保留恢复业务约束和 Room 校验所需的空结构定义。
- 偏好保持 Android 原始 XML，附件保持二进制，二者没有 JSON 等价格式。

### 手动编辑规则

- 修改：直接编辑文件内容，保存回 ZIP 即可。
- 删除：删除文件即删除该条目；指向它的子记录（如该角色的聊天）会在恢复时按外键一并移除，并写入详情日志。
- 新增：复制一个文件并删除其中的 `rpclient_backup` 键，恢复时自动分配新主键。复制文件但保留 `rpclient_backup.id` 时，重复主键会被重新分配并记录警告。
- 新增聊天文件且没有来源角色 ID 时，先按唯一指纹、再按唯一角色名匹配；也可以在头行 `rpclient_backup.session.characterId` 指定来源角色主键。明确指定的来源 ID 缺失或重复时跳过聊天，不会改绑同名角色。
- 单聊图片以 JSONL 的图片数组为准，编辑、删除和复制文档后重新建立附件关系。内嵌原图经解压大小、摘要与实际格式校验后保存在附件目录；纯哈希引用只能读取归档内已有的附件，不下载外部 URL。无法找到本地字节的引用会跳过并记录警告，损坏的内嵌图片会使恢复在覆盖前失败。
- 群聊图片关系按唯一来源消息重新关联；群聊文档或消息被删除、来源有歧义时移除图片关系，避免后续新消息复用数字 ID 时继承旧图片。
- 世界书的 `rpclient_backup.entryCategories` 按条目键保存本地分类 JSON，与 `entryIds` 使用同一键。菜单协议中的高级设置以当前实体为准，清空设置不会从历史原始 JSON 中恢复旧值。
- 新增故事且没有对应本地关系附加信息时，使用文档中的 `characterHints`、`lorebookHints` 按菜单规则匹配唯一角色或条目；保留激活方式和顺序，不继承其他故事的时序状态。已有本地关系继续严格按来源 ID 解析，缺失或歧义会记录警告。
- 角色作用域正则只存在于角色卡里，恢复时以卡内内容为准。绑定的世界书以 `worldbooks/` 下同一本为准；只有该文件缺失时才使用角色卡内嵌的副本，并记录警告。
- 完整备份的角色卡使用 `data.first_mes` 保存首条主开场白，`rpclient_backup.additionalFirstMessages` 数组保存 `<START>` 分隔的后续主开场白，恢复时保留原始空白与空段。修改首条只需编辑 `first_mes`；备用开场白仍使用 `alternate_greetings`。旧 v3 未包含附加数组时沿用既有角色卡读取规则，之前已丢失的内容无法补回。
- 恢复仍会检查路径安全、重复条目、SQLite 完整性、外键以及 Room 迁移兼容性。不兼容的数据库在暂存目录被拒绝，不会覆盖当前数据。

### 兼容旧格式

仍可恢复 portable v2（只读）、V1 JSONL 快照和原始 SQLite 快照。v2 沿用校验和与 `_tableRows`，不支持手动编辑。新的导出一律为 v3。

## 恢复与失败处理

完整恢复会覆盖两套数据库、偏好、附件和应用私有文件，随后重启应用。需要保留当前数据时，应先另存一份备份。

恢复时先将压缩包暂存到缓存，再读取 ZIP 中央目录并核对文件大小和 CRC。传输截断或内容损坏会在覆盖前报错。归档校验和迁移在独立暂存目录进行。通过校验后先关闭数据库，再保存回滚副本，避免遗漏 WAL 中已提交的数据。替换失败时尝试恢复所有条目；若回滚本身失败，则保留缓存目录中的回滚副本，不将其作为普通临时文件删除。数据库关闭后的路径都要求重启，不能继续使用旧连接。

完整恢复后默认关闭搜索加速，普通搜索直接扫描恢复后的正文。所有现有恢复格式都在暂存库中清空搜索词条、来源和构建进度，忽略旧归档携带的搜索状态；恢复和重启均不会自动登记或重建索引。需要加速时，由用户在设置中手动开启，再从当前内容完整构建索引。

请求日志的请求与响应正文按 UTF-8 字节分块读取，避免完整行超过数据库游标窗口。每个正文上限为 16 MiB，超限时导出失败，不截断正文，也不会覆盖目标旧备份。

## 角色卡批量传输

- 角色管理页导出的 ZIP 内是独立角色卡 JSON，单独或批量导出仍遵循普通角色卡规则；完整备份的额外主开场白扩展仅用于完整恢复。
- 角色 ZIP 的导入和导出最多允许 1,000 个条目、64 MiB 压缩数据、每张 JSON 8 MiB、累计实际读取 JSON 32 MiB。导出先在缓存中完成封包并核对限额，通过后才写入所选文档。
- 批量导入按角色卡格式和旧版角色字段识别 JSON。普通清单和世界书计入失败，误选完整备份时整包拒绝。
- 导入时单卡超限或格式损坏计入失败并继续读取后续角色；压缩包、累计大小或条目总数超限时拒绝整包，不保存部分草稿。所有退出路径均清理临时 ZIP。

## 模块职责

- `BackupRestoreActivity` 只负责系统文件选择和重启；ViewModel 管理操作、确认弹窗与本地化状态。
- `PortableBackupRepository` 编排导出和恢复；`BackupV3Writer` / `BackupV3Reader`（`PortableBackupV3.kt`）按各菜单的编解码器读写文档。
- `ChatArchiveCodec` 在同一轮解析中交付单聊正文和本地关联信息。完整恢复按归档字节限额读取长会话，单聊菜单导入上限为十万条消息。`BackupImageStore` 在暂存目录中处理图片，复用 `MessageImageValidator` 的格式约束。
- `BackupReport` 收集阶段日志与警告；页面在备份和恢复结束后以可展开、可复制的区块展示，失败时仅附固定错误类别和异常类型，不透传原始异常消息、输入内容或堆栈。恢复成功后由用户点击按钮重启，警告不会随进程消失。
- `BackupDatabaseCodec` 处理业务结构和数据行，过滤派生搜索数据；`BackupDatabaseValidator` 使用正常 Room 迁移校验暂存数据库，并统一关闭搜索加速、清空检索缓存。
- `BackupArchiveFiles` 处理 ZIP 和文件校验；`BackupDataReplacer` 统一执行新旧格式的替换与回滚。
- 新增文案放在各语言既有的 `strings.xml`，不另设备份或 Markdown 专用资源文件。

## 数据隐私

ZIP 不加密，可能包含 API Key、自定义请求头、提示词、对话、原始请求响应日志和附件。获得归档的人可以读取这些内容，请妥善保存，勿公开发布。

## 回归验证

设备测试使用独立临时目录和真实 SQLite，覆盖完整往返、搜索数据不导出、恢复默认关闭加速、旧归档搜索数据忽略、用户手动重建索引、背景附件、私有同名 manifest、无效归档、未来数据库版本、损坏行数据、多开场白、超大日志、世界书分类与空值、角色缺失或歧义、单聊图片编辑和复制、群聊孤立图片、故事提示匹配，以及替换失败后的 WAL 回滚。角色 ZIP 单元测试覆盖大小边界、伪造条目大小、损坏卡片容错、累计预算与取消清理。测试不读取或恢复用户实际数据。

## 混淆（R8）注意

备份用 Gson 按“字段名 = 数据库列名”读写 `libs/room/entity` 下的实体，因此 `proguard-rules.pro` 保留了这些实体的字段名。去掉该规则后 release 包会读到全为 null 的实体；导出时会在首次映射某个实体时校验字段名，并在备份详情中给出明确原因。
