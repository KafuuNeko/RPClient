# 群聊创建对话分支功能调研

> 调研及实施日期：2026-11-21。调研代码基线：`9b915017`，应用版本 `2026.4.4`。范围为群聊分支的交互、数据复制与验证方案，实施结果见文末。

## 建议处理方式

沿用单聊的独立会话快照机制：在群聊消息操作栏加入“从这里分支”，复制截至所选消息的完整历史前缀，并打开新的群聊。所选消息包含在副本中，源会话的持久化数据保持原样。在最后一条消息操作，相当于克隆完整对话；在中间消息操作，则创建截断到该位置的分支。

现有表结构足以承载该功能，无须新增父子会话关系、修改数据库版本或引入统一分支框架。主要工作是补齐群聊仓库的事务复制、摘要查询、图片类型参数和页面入口，复杂度集中在数据一致性。

- 复制新的会话记录、独立的成员关系、消息记录及分支点有效的最新摘要。
- 图片创建独立 UUID 引用，共享底层文件字节；双方删除、编辑互不误伤。
- 复制当前已保存的会话设置，重置世界书运行时状态，不继承正在执行的生成任务。
- 复用通用导航事件及现有分支文案，保持项目的 MVI 分层。

## 分支复制规则

| 数据 | 建议规则 |
| --- | --- |
| 会话身份 | 创建新的会话 ID；标题使用 `toDefaultChatTitle()`，与当前单聊分支一致；`createTime`、`latestTime` 使用分支创建时间 |
| 会话设置 | 复制场景、用户笔记、人设绑定及描述覆盖、世界书条目选择、三种 Prompt 覆盖、发言策略、角色卡模式和各项开关 |
| 用户名称 | 与单聊一致，在事务内解析当前有效名称写入分支，避免旧用户消息缺少署名时改变显示；保留原人设绑定及描述覆盖规则 |
| 世界书运行时 | 将 `worldInfoStateJson` 重置为 `{}`；保留条目选择，不直接继承源会话后续剧情积累的 sticky/cooldown 状态 |
| 成员关系 | 复制当前 `GroupChatMember`，保留 `characterId`、`sortOrder`、`muted`，仅替换 `sessionId` |
| 消息 | 按 `(createTime, id)` 稳定顺序复制截至所选消息的前缀，分配新 ID，保留原始正文、来源、角色 ID 和历史名称快照 |
| 生成批次 | 将每个非空 `generationBatchId` 映射为新的 UUID；同一旧批次在分支中的消息继续共享同一新批次，空值保持为空 |
| 图片 | 为每个复制的附件创建独立文件索引 UUID，保留 `position` 和文件元数据，共享原图 hash |
| 摘要 | 只复制分支点有效的最新快照；非零 `coveredMessageId` 必须映射为新消息 ID，零边界保持为零 |
| 页面临时状态 | 输入草稿、编辑草稿、待发送图片、流式占位任务、待执行发言者列表、重试上下文、搜索定位和 Prompt 检查缓存均不复制 |

这里的设置和成员取自分支创建时的当前持久化状态。[GroupChatMember](../app/src/main/java/me/kafuuneko/rpclient/libs/room/entity/GroupChatMember.kt#L31) 没有历史修订记录，不能恢复所选消息产生时的成员名单、静音状态或当时的场景设置。世界书运行时也只保存会话当前状态，重置后的时序效果重新计算，不代表恢复当时的运行时快照。以后若需要真正回到历史配置，需要另行设计修订或事件记录。

角色卡、人设库、世界书内容仍按现有全局资源引用，不克隆这些资源本体。因此“分支独立”覆盖会话记录、成员关系、历史消息、摘要和图片引用，不意味着建立一套互不关联的角色资源。已经退出群聊或被删除的历史发言者仍保留消息内的 ID 和名称快照，不根据历史消息把他们重新加入成员列表。

## 仓库事务与消息边界

在 `GroupChatRepository` 增加与单聊同名的 `createBranchSession(sourceSessionId, throughMessageId, title, createTime)`。建议沿用返回新 ID、校验不通过返回 `0L` 的现有契约；数据库及文件索引异常继续抛出，由 ViewModel 映射为失败提示。

事务必须从 `mImages.mutate { ... }` 进入。该入口已经按“文件锁、Room 事务”的顺序协调文件索引和数据库，不能在外部先开 Room 事务再调用它，以免逆转锁顺序。参考 [FileRepository.mutate](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/FileRepository.kt#L327)。

- 在同一事务中读取源会话、所选消息和当前成员；确认消息属于源会话且仍然存在，在任何写入前完成校验。
- 按数据库的稳定顺序取得所选位置的完整前缀。不得从 `conversationState.messages` 复制，因为页面可能只加载了一页，或正停留在搜索结果附近。
- 读取该前缀有效的摘要，插入新的会话及成员关系。
- 按原顺序批量插入消息，建立旧消息 ID 到新消息 ID 的映射，同时维护批次 ID 映射。
- 使用带类型的图片复制方法，最后插入重映射边界后的摘要，整体提交。

首版可以沿用单聊“从完整有序历史截取前缀”的方式；不新增长期缓存或通用快照系统。若较早的分支点仍导致大量无关后缀被读取，再给 DAO 增加按目标 `(createTime, id)` 截断的查询。长历史验收应记录耗时和内存表现。

### 复制后的时间顺序

不要直接照搬单聊的 `createTime + index`。假设复制两千条消息，最后一条会被排到分支创建时刻约两秒以后；若用户立即发送新消息，它可能按时间排序插进复制历史中间。群聊的[消息查询和分页](../app/src/main/java/me/kafuuneko/rpclient/libs/room/dao/GroupChatMessageDao.kt#L29) 都按创建时间及 ID 排序，这会影响消息尾部、分页和发言者判断。

建议仍按原顺序重建消息时间，但将末条放在分支创建时刻：`messageTime = branchCreateTime - (prefixSize - 1 - index)`。这样复制消息的相对顺序稳定，且在系统时钟正常前进时，新回复排在完整前缀之后。会话的创建时间及最近活动时间均保持为 `branchCreateTime`。

### 摘要必须包含相等边界

不能直接复制 `getLatest(sessionId)`，因为最新摘要可能覆盖分支点之后的消息；也不能直接用当前 `getPrevious()`，因为它使用严格小于，会漏掉恰好覆盖到所选消息的有效摘要。

新增 `getLatestAtOrBefore(sessionId, throughMessageId)`，按摘要 ID 倒序选择有效快照。群聊历史按 `(createTime, id)` 排序，摘要边界也应属于相同前缀；以下 SQL 表达这一规则，避免额外假定历史时间与消息 ID 永远同序：

```sql
SELECT summaries.*
FROM group_chat_summaries AS summaries
JOIN group_chat_messages AS target
  ON target.id = :throughMessageId
 AND target.sessionId = summaries.sessionId
LEFT JOIN group_chat_messages AS boundary
  ON boundary.id = summaries.coveredMessageId
 AND boundary.sessionId = summaries.sessionId
WHERE summaries.sessionId = :sessionId
  AND (
      summaries.coveredMessageId = 0
      OR boundary.createTime < target.createTime
      OR (
          boundary.createTime = target.createTime
          AND boundary.id <= target.id
      )
  )
ORDER BY summaries.id DESC
LIMIT 1
```

最新的空摘要也是有效快照。[updateCurrentSummary](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/GroupChatRepository.kt#L1061) 将用户主动清空摘要表示为内容为空、边界为 `0` 的记录；查询不能加非空内容过滤，否则会错误恢复旧摘要。边界为零的语义与单聊一致，表示当前声明的无消息覆盖状态，不用于推断快照的历史生效时间。

复制时仅将非零边界映射到新消息；不能把映射失败静默降为零并继续保留原摘要内容。摘要应在分支事务内直接写入，不能调用要求边界必须指向真实消息的 `saveSummary()` 处理零边界。分支只继承一份有效快照，创建后不会立即拥有源会话的整段摘要回滚历史。

### 图片复制必须区分消息类型

将现有 `copyInTransaction` 扩展为显式接收 `MessageType`，并将该参数同时用于源附件查询、目标消息归属校验和附件关系写入。单聊调用处显式传 `Single`，群聊传 `Group`。

单聊和群聊的消息 ID 是两套独立空间，数值可以相同。旧方法用于群聊时会读取单聊附件，可能校验失败，也可能在 ID 恰好重合时读取错误关系；不能只在调用方把群聊 ID 填入现有映射。

沿用 [Mutation.copyReference](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/FileRepository.kt#L402) 的独立 UUID 与共享 hash 机制，不复制文件字节，也不让两个消息共用同一个附件 UUID。保留现有批次大小及位置顺序，不通过带“四张图片”编辑限制的 `replaceInTransaction` 重建历史附件，以免给已有导入消息的分支引入回归。复制接口不按 User、Character、System 来源额外限制附件。

### 批次和自动发言

允许在多角色同一批次的中间分支，仅复制用户选定的前缀，不自动带入该批次后续回复。当前 `generationBatchId` 用于记录生成批次，没有发现按它继续执行历史任务的读取逻辑；重映射是为了保持新会话的批次标识独立。

保留 `autoModeEnabled` 配置，但打开分支不自动启动请求。源会话正在执行的生成循环不能迁移到新会话。下一次用户操作时，[getSpeakerSelectionData](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/GroupChatRepository.kt#L392) 会从分支自己的历史重新计算 Pooled 发言池和最近发言者，无须复制内存游标。

## 页面接入和失败恢复

在 `GroupChatUiIntent` 新增 `BranchFromMessage(messageId: Long)`，由 ViewModel 响应，Compose 只负责展示按钮和发送 Intent。

建议群聊全部已持久化消息都开放分支，包括第一条开场白；群聊可包含多条角色开场消息，直接套用单聊的“首条不可分支”规则没有明确的数据约束依据。不得把当前分页窗口的第一条当成完整历史首条。流式消息和代写预览不开放分支，仓库仍需再次验证真实消息归属。

处理函数应要求当前处于会话页、没有其他业务弹窗、没有正在编辑的消息，且图片协调器没有忙碌的处理或提交任务。使用 `mGenerationJob` 作为生成互斥依据，因为群聊的[摘要](../app/src/main/java/me/kafuuneko/rpclient/feature/groupchat/GroupChatViewModel.kt#L1479)和[用户代写](../app/src/main/java/me/kafuuneko/rpclient/feature/groupchat/GroupChatViewModel.kt#L1267)也共用该 Job，不能只判断界面上的 `Generating` 状态。

给 `GroupChatDialogState` 增加 `Branching`，在 `GroupChatLayout` 复用 `LoadingDialog`。当前 `Saving` 的说明写死为“群聊设置”，不宜直接用于分支；新状态可复用现有 `saving` 和 `branch_from_message` 资源。操作保持忙碌态直到导航或失败恢复，避免队列中的重复点击创建多个副本。

导航优先复用 `AppViewEvent.StartActivity(GroupChatActivity::class.java, extras)`，使用 `EXTRA_SESSION_ID` 传入新 ID；`emitAndAwait()` 确认事件处理完成后发布 `GroupChatUiState.finished(...)` 结束源页面。这与[群聊创建页现有导航](../app/src/main/java/me/kafuuneko/rpclient/feature/groupchatcreate/GroupChatCreateViewModel.kt#L617)一致，可直接使用已有宿主能力，不必新增 `GroupChatViewEvent.OpenSession` 或修改 `GroupChatActivity`。

- 返回 `0L` 或出现文件索引、数据库异常时，恢复操作前的页面快照，显示现有 `branch_create_failed`，保留源页输入、附件草稿、历史窗口和搜索定位。
- 处理失败时不要使用会丢弃页面草稿的无条件全量初始化，也不把异常原文展示给用户。
- 协程取消继续传播；不得捕获取消后当作普通失败继续导航。
- `FileRepository.mutate` 的提交段使用 `NonCancellable`。事务开始前取消可停止创建；已进入提交段后，取消仍可能留下完整且有效的分支，不能把“取消必定零写入”作为契约，也不能删除已经提交的共享文件引用。

源页未提交的输入和待发送附件不属于分支内容。成功后与单聊一致结束源页；验收需覆盖有输入草稿时的行为，不能把未发送内容悄悄作为新消息写入分支。

`branch_from_message`、`branch_create_failed`、`generation_already_running` 已覆盖默认英文及全部十二种支持语言。默认日期标题与当前单聊行为一致；现有 `branch_session_title` 虽然存在，当前单聊实际没有使用。若后续调整标题或增加专用提示，需同步两种聊天的产品行为，并补齐全部语言。

## 验收与必要测试

| 场景 | 验收要点 |
| --- | --- |
| 中间消息及最后消息 | 中间分支准确包含截至所选消息的前缀，末条分支复制完整历史；源数据不变；返回首页可见新群聊 |
| 搜索与备份恢复 | 搜索可定位分支中的独立消息；整库备份恢复后，两份群聊、摘要边界及图片引用仍正确 |
| 首条和多角色开场 | 第一条可创建只有一条消息的分支；不会补写其他开场白，不重新走 `createSession` 的开场规划 |
| 分页和搜索定位 | 在较早页或搜索附近分支，仍复制数据库的完整前缀，不只复制已加载窗口 |
| 成员及历史署名 | 顺序和静音状态保留；双方调整成员关系互不影响；已退出或删除的角色不会重新加入；历史名称不被当前卡名覆盖 |
| 摘要边界 | 验证分支点早于、等于、晚于摘要边界；较新的越界摘要不能进入分支；复制后的覆盖 ID 必须指向新会话消息 |
| 空摘要与异常边界 | 主动清空不会恢复旧摘要；零边界保持零；跨会话或缺失边界不能带入不对应的摘要内容 |
| 图片隔离 | 验证单聊与群聊同数值 ID、各来源消息的附件、有序多图和历史超四图；新旧 UUID 不同而 hash 相同 |
| 删除和编辑 | 分别先删除源会话、先删除分支；剩余会话的图片可读，最后一个引用删除后按现有规则回收；编辑分支不改变源消息或源摘要 |
| 多角色批次 | 批次中间分支不包含后续回复；批次 ID 映射保持分组；Pooled 及最近发言者按分支历史计算 |
| 长历史后继续聊天 | 大量复制消息的时间不晚于分支创建时间，新发言位于尾部，分页和摘要查询不乱序 |
| 无效消息及事务失败 | 消息已删除、来自其他会话，或中途写入失败时，不留下半成品会话、成员、摘要或附件索引 |
| 忙碌和重复点击 | 回复、自动循环、摘要、代写和图片处理期间无法启动分支；连续点击只创建一份；错误恢复后可以重试 |
