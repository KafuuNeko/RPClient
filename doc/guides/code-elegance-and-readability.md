# 代码美观与可读性规范

本文约定命名、参数表达、控制流及 Compose 代码的可读性要求。自动排版使用 Android Studio 原生格式化器及项目代码样式，配置和执行方式见 [自动代码格式化](./code-formatting.md)。

## 排版与语义

- 缩进、折行、括号位置、尾逗号及声明间距由格式化工具统一处理。
- 参数名、解释性变量、卫语句和业务控制流需要结合类型、作用域和求值顺序审查。
- 命名调整应考虑调用关系与 API 兼容性。

## 表意清晰

- 名称说明对象的角色和行为，避免含义不明的缩写及重复内联完整包名。
- 布尔值、数值、null 和多个同类型参数容易混淆时，在 API 支持的情况下使用具名实参；参数名应帮助理解调用。
- 条件包含多个业务判断时，按含义拆成解释性变量；复用值或需要表达业务概念时再提取局部变量。
- 优先用提前返回、continue 等卫语句减少嵌套，保持主要流程清晰。
- Lambda 嵌套时明确参数含义，避免多个隐式 it 相互混淆；保留必要的类型推断、接收者和返回目标。

## Compose 与集合处理

- Compose 按可观察状态渲染和发送事件，复杂计算不堆进组件参数。
- 多个回调或内容槽位容易混淆时使用具名参数说明用途。
- 集合操作和作用域函数应清晰表达数据流，避免堆叠 let、run、also、apply 隐藏流程层次。
- 字符串模板里避免嵌入复杂业务计算，先计算有意义的展示值再拼接。

## 审查与验证

- 审查名称、参数和控制流是否清晰，特别关注嵌套作用域与返回目标。
- 审查 diff 是否符合任务范围，确认求值顺序、作用域和业务行为正确。
- 根据受影响范围运行已有编译和测试，不把格式检查通过当作业务等价证明。
- 注释与 KDoc 遵循 [代码注释与 KDoc 规范](./comments-and-kdoc.md)，解释意图、边界和必要约束，避免复述代码。
