> 调研日期：2026-09-09
>
> 代码基线：`42ccdb0`
>
> 文档性质：原始调研与已确认设计；实现进度以任务表为准，`FILES` 工程记录更新于 2026-09-10。
>
> 约束：保留 `ChatMessage`、`GroupChatMessage` 表结构；图片交给 `FileRepository`；新增消息图片关联表；当前未发布的 Room version 保持 `4`。

## 结论与已确认决策

推荐采用“本地原图 + 消息图片关联表 + 有序多模态内容块 + 三协议内联图片”的方案。

- 原图由 `FileRepository` 按文件内容哈希保存，发送前生成经过缩放、方向校正和元数据清理的版本。
- 在用户提出的 `messageId`、`messageType`、`imageUuid` 基础上增加 `position`，明确同一消息内的图片顺序。
- 一条消息仍然保存一份文本正文，图片独立关联；支持纯图片消息和文字附图消息。
- Prompt 和 LLM 运行时采用有序 `Text` / `Image` 内容块。图片不写入正文、不伪装成 Markdown 链接，也不把 Base64 存进 Room。
- 继续使用现有 OpenAI Compatible、Gemini、Anthropic Messages 适配器，分别生成对应的图片输入结构。首次接入不需要图床、上传服务器或切换 API 类型。
- 图片随所属历史消息进入后续请求，参与预算裁剪；摘要模型也读取图片，将相关视觉信息写入文字摘要。
- 明确不支持图片的模型阻止含图请求；能力未知时允许尝试，由接口错误反馈。不得自动忽略图片或偷偷切换模型。

用户已确认下列产品决策，后续实现无须重复询问：

| 决策 | 确认结果 | 直接影响 |
| --- | --- | --- |
| 原图保存 | 保留原图，发送时生成处理版本 | 本地可以查看原始细节，处理版本可重建；增加原图存储占用 |
| 历史与摘要 | 图片随历史发送，摘要直接读图 | 后续回复可以引用图片；摘要请求也需要视觉能力并产生图片输入用量 |
| 非视觉模型 | 已知不支持则拦截，未知则尝试 | 覆盖新消息、历史图片、摘要、重生成和群聊各发言模型 |
| 数据库版本 | 当前未发布版本不升级 Room version | 在现有 version `4` 内完善 schema，维护已发布旧版本到最终 `4` 的迁移 |

其余数量、尺寸和模块命名是本文给出的工程建议，不是已有实现或服务商保证。

## 接口契约与层间调用约定

本节补齐后续实施需要的对象所有权与调用边界。调用入口、文件锁与事务顺序、支持格式、资源限制、模型能力和验证范围已在本文对应章节完成调研，直接复用，不再作为任务表中的准备阶段。下列名称是建议命名，描述的是待实现契约，不代表已有接口。

### 跨层对象与所有权

| 对象 | 最小信息与用途 | 所有权和生命周期 |
| --- | --- | --- |
| `MessageKey` | 稳定的 `messageType` 与真实 `messageId`；单聊和群聊即使 ID 相同也不能混用 | 由消息 Repository 校验父消息、用户来源和所属会话；未提交草稿使用独立草稿标识，不伪造消息 ID |
| 图片草稿描述 | 草稿 ID、图片顺序、准备状态、预览引用和可展示错误 | 页面状态只保存轻量描述；`FileRepository` 管理暂存原图，移除、放弃及恢复时通过数据层释放或重新校验 |
| `PreparedFile` | 暂存句柄、原图 hash、实际 MIME、字节数及校验结果 | 属于一次导入／提交操作，尚不是永久 `FileEntity`；提交成功后转为消息附件所有权，失败时保留可重试草稿或清理该操作独占资源 |
| 图片元数据 | 原图尺寸／方向与发送版本尺寸／MIME／精确字节数分开表达，携带缓存规则版本 | 图片处理服务生成并缓存；可从原图重建，不增加消息表字段，不把临时 URI 当作持久标识 |
| 消息及附件聚合模型 | 消息正文、`MessageKey`、按 `position` 排序的附件与文件索引快照 | Repository 在一致读取事务内组装，ViewModel 再映射为 UI model；Prompt 准备层使用同一领域输入，不逐图查 DAO |
| `PreparedImageRef` | 不可变发送资源标识、处理规则版本、MIME、尺寸和字节数 | 在 `libs/llm/model/` 表达通用请求引用；通过受控 resolver 访问，不携带 Room Entity、Android URI、Bitmap、流或 Base64 |
| 图片读取租约 | 对本次使用的原图／派生文件实施回收保护，提供受控读取能力 | 由文件／图片服务管理；预览与请求分别申请、分别释放，不因界面销毁提前释放仍在发送的资源 |

`PreparedImageRef` 是可传递的不可变值，读取租约是需要关闭的运行时资源，两者分开。暂存图和已提交附件都可以解析为发送引用，但只有事务提交后才获得正式消息归属；分支通过新消息 ID 和新 UUID 建立自己的附件关系。

### 数据提交与失败责任

| 调用边界 | 输入与输出 | 责任约定 |
| --- | --- | --- |
| 文件准备 | 系统选择结果 → `PreparedFile`／结构化失败 | `FileRepository` 封装限量复制、暂存和 hash；图片处理服务负责解码、方向与发送版本；IO 均在 Room 事务之外 |
| 消息新建／编辑 | 会话或 `MessageKey`、正文、有序已准备图片／既有附件 → 已提交消息聚合结果 | `ChatRepository`／`GroupChatRepository` 编排一个事务，校验归属并写入正文、文件索引、附件关系及必要的摘要失效；编辑保留的旧附件验证属于原消息 |
| 引用复制／删除 | 原附件 UUID 或待清理消息集合 → 新引用或待回收 hash 集合 | 共享附件协调能力封装关系表操作，并复用 `FileRepository`；角色删除、会话清理、分支和截断均加入调用方同一个事务 |
| 请求图片准备 | 已选消息快照、Provider 配置快照、处理规则 → 有序发送引用与预算元数据 | 图片准备层完成 IO，Builder／Finalizer 只处理值对象；最终发送使用相同版本资源，不能预算后重新选择另一种压缩方案 |
| 请求执行 | 最终请求 → 回复／流式事件／结构化失败 | 共用请求准备入口执行能力和大小检查，Adapter 负责协议编码与 HTTP；持久化的用户消息不因网络失败回滚 |

具体责任落实如下：

- 消息 Repository 对事务原子性负责；文件服务对可靠落盘、租约和物理回收负责。所有涉及文件索引的写入沿用“先协调锁、后短 Room 事务”，内部已持锁操作不能再次获取同一非重入锁。
- 共享附件协调能力可命名为 `MessageImageRepository`，依赖 `AppDatabase` 和 `FileRepository`；由聊天、群聊及角色 Repository 调用，不反向依赖这些业务仓库。事务内附件操作与事务后回收分开，避免嵌套入口重新加锁。
- 提交结果必须以数据库是否真正提交为准。若取消发生在提交完成与返回结果之间，数据层仍完成最小的提交状态登记，不能把已提交资源按失败草稿清理；页面恢复通过已保存消息重建状态。
- 提交前失败保留可重试草稿；提交后网络失败使用同一消息重试生成。重复点击通过发送状态及提交中的草稿所有权阻止重复提交，不把网络重试重新解释为创建用户消息。
- 非流式请求在返回或失败时释放租约；流式请求在实际收集结束、失败或取消时释放，不能在返回尚未收集的 `Flow` 时关闭资源。请求临时文件随该请求回收。
- 协程取消继续向上传播，不映射成普通模型失败。其他错误区分格式、资源缺失、能力不足、单图限制、请求预算和网络响应，并由 ViewModel 转换为可操作的脱敏提示。

### FILES 阶段已落实的工程细节

- `PreparedFile` 使用草稿所有者和不包含路径的句柄管理暂存；文件内容流式计数、计算 SHA-256 并同步落盘。输入 MIME 暂作为索引提示，实际图片格式识别与像素校验由 `MEDIA` 完成，不能把当前 MIME 当成已验证格式。
- 原图发布使用仓库同目录临时文件，复核暂存哈希、同步写入并检查 `renameTo()` 结果。短 Room 事务前保留 staging 副本，事务失败可直接重试；成功提交后消费句柄及其暂存资源，数据库 UUID 再次校验防止残余元数据导致重复提交。
- 文件锁统一先于 Room 事务；事务开始前响应取消，已开始的短事务与成功登记使用不可取消收尾。物理回收同时检查全部文件索引和目录共享的读取租约；分支只复制 UUID 索引，不复制原图字节。
- 启动时回收无文件索引且无读取租约的孤立 hash、旧保存临时文件及发布中断文件。无活跃所有者的 staging 暂保留 `24` 小时供进程恢复，过期后清理；活跃草稿不受该超时影响，用户放弃草稿立即释放。该保留期是本地恢复策略，不是服务商限制。
- `MessageImageRepository` 提供消息与附件一致批量读取；消息和文件查询参数按最多 `900` 个分批。单聊和群聊新聚合分页入口沿用 `createTime + messageId` 游标，图片数不改变分页或摘要边界单位。

### Prompt 与协议的共同边界

当前 [LLMRepository.kt](../app/src/main/java/me/kafuuneko/rpclient/libs/room/repository/LLMRepository.kt) 负责请求后处理，[LLMClientFactory.kt](../app/src/main/java/me/kafuuneko/rpclient/libs/llm/LLMClientFactory.kt) 装配适配器及用量统计。沿用这些入口接入共享能力，不在单聊、群聊或每个 Adapter 各自实现一套图片规则。

- 将 Gemini／Anthropic 的角色正规化提取为保留有序内容块及来源信息的公共纯逻辑，并前移到 Finalizer 的预算计算之前。领先 system、角色降级、同角色合并及必要占位产生的内容都纳入最终结果和检查器。
- 已标记 `isPromptFinalized` 的请求不再由 Adapter 重写内容或轮次；Adapter 只将正规化结果映射成协议字段。未经过 Finalizer 的既有入口由 `LLMRepository` 调用同一后处理／正规化逻辑，避免纯文本调用出现不同语义。
- 请求准备固定 Provider 配置、图片处理规则和发送引用；最终 JSON 在应用受保护字段规则的 Patch 后计量，检查器与实际请求引用同一内容计划。若准备结果改变入选范围，必须重新最终化，不能直接替换发送内容。
- 图片 resolver 的接口归通用请求层，文件实现归数据／图片服务层，通过构造注入接入；网络 Adapter 不直接读取 DAO。日志从脱敏结构生成，不复用含图片字节的请求字符串。

### 配置与编码约束

- 图片输入自动／支持／不支持设置保存在 `LLMProvider`；可空输入模态属于模型目录信息，缓存作用域沿用本文的 Provider／地址／model 规则。
- 格式、数量、尺寸、输入字节、请求字节及未知模型每图 `4096` Token 回退估算集中到共享图片策略配置，由 UI 校验、处理器、预算器和发送层使用同一份规则。首版不增加单独的质量配置页面；可调整是集中参数能力，不要求新增持久化业务表。
- 暂存句柄、图片元数据和读取租约不写入 `AppModel`。已有全局偏好仍按 Kotpref 规范管理，图片业务数据保持在 Repository／缓存中。
- 编码严格遵循 [coding-guidelines.md](./coding-guidelines.md) 及其相关专题：Compose 渲染并发送 Intent，Activity 处理选择器 ViewEvent，ViewModel 调用数据层；共享 Repository／服务在 `RPClientApp.kt` 注册 Koin，ViewModel 沿用 Activity 的 `viewModels()` 创建。
- 核心类和公共接口按规范补充中文 KDoc，跨存储提交、取消、预算和协议差异写明必要约束；方法超过 `16` 行时添加分步行内注释，文档与注释使用无序列表。Room version 继续遵循用户明确指定的未发布版本例外，不升级。

## 数据模型与引用生命周期

### 消息图片关联表

建议新增 `MessageImageEntity`，表名 `message_images`：

| 字段 | 建议类型 | 规则 |
| --- | --- | --- |
| `messageId` | `Long` / INTEGER | 指向所属类型的消息 ID；正式记录必须关联已存在的消息 |
| `messageType` | 稳定枚举编码 / TEXT | 建议保存 `single`、`group`，显式 Converter；不要依赖 enum ordinal |
| `imageUuid` | `String` / TEXT | 指向 `files.uuid`，保存原图文件索引；不是哈希、URI 或远端 file ID |
| `position` | `Int` / INTEGER | 非负，按用户草稿中的显示顺序保存；查询必须显式排序 |

约束建议：

- 联合主键为 `(messageType, messageId, position)`，天然允许同一消息关联多张图片，并支撑按消息读取的前缀索引。
- 为 `imageUuid` 建唯一索引，落实下文“一条附件关系拥有一个 UUID”的规则。
- `imageUuid → files.uuid` 建普通外键，删除策略使用 `NO ACTION` / `RESTRICT`，先删关系再释放文件索引；不要通过删文件悄悄删掉消息图片。
- 不以 `(messageType, messageId)` 唯一，也不依赖 SQL 默认行顺序。
- `position` 仅表示图片之间的顺序。本期 UI 是“有序图片组 + 一段文字”，不承诺任意段落间插图；不需要给旧消息正文建立富文本位置映射。
- 首次接入只允许单聊 `Source.User`、群聊 `Source.User` 拥有本地图片附件。模型输出图片、系统图片和角色卡自动作为图片输入另行设计。

`messageType` 决定消息表，SQLite 外键无法通过列值动态选择父表；给 `messageId` 同时声明两个外键也不是“二选一”。因此消息一侧采用 Repository 事务校验与显式清理，文件一侧使用真实外键。该结论由 SQLite 固定父表的外键定义推导而来。[SQLite 外键文档](https://www.sqlite.org/foreignkeys.html)

不推荐为了双向级联，改成两个可空消息 ID 字段或拆出两张图片表：这会偏离已确认的数据方向。首次实现也不额外引入维护消息关系的 SQL trigger；应明确把所有删除入口纳入同一数据层契约。

### 去重应沿用物理文件共享，而不是贸然全局共享 UUID

现有行为是：

```text
消息甲的图片索引 UUID-A ─┐
                       ├─ 同一个 SHA-256 ─ 原图物理文件
消息乙的图片索引 UUID-B ─┘
```

两份 `FileEntity` 是轻量索引，不是保存了两份图片。SHA-256 去重针对相同字节，像素看起来相同但 EXIF、编码或压缩不同的图片不保证去重。

推荐保持该语义，增加类似 `duplicateReference(uuid)` 的能力：创建新 UUID 指向既有 hash，不读取、复制或重新压缩原图。分支、再次引用既有图片、导入同一资源时都可以复用此能力。

选择该方案的依据：

- `deleteFile(uuid)` 当前只统计同 hash 的 `FileEntity` 数量，不会统计业务表里同一 UUID 被引用了多少次。
- 如果多个消息甚至头像直接共享同一 UUID，任何调用方删除它都可能让其他对象失去文件索引。
- 使用独立 UUID 不需要在本次改造里重做头像、角色卡等全部文件引用机制。
- 唯一索引只能约束消息图片表内部；Repository 仍必须禁止直接借用头像 UUID，引用既有资源时创建自己的索引。

若以后确实要实现“同 hash 只有一个 UUID”，应单独完成全局引用登记与释放机制后再调整，不能只给 `files.hash` 添加唯一索引。

### 文件与 Room 的提交边界

Room 事务无法回滚文件系统操作。推荐把原图导入分成“准备文件”和“提交索引”，由消息仓库编排最终事务，`FileRepository` 提供底层准备、索引和回收能力。

```text
选图 URI
  → 限量流式复制、计算 hash、验证可解码性
  → FileRepository 管理的待提交原图与草稿句柄
  → 生成缩略图及本次发送版本，完成请求预检查
  → 同一 Room 事务：创建用户消息 + FileEntity + message_images
  → 清空已提交草稿，开始模型请求
```

- URI 读取、解码和压缩不放进长 Room 事务。临时原图由 `FileRepository` 管理的 staging 区持有，UI 只持有不透明草稿 ID。
- 原图在数据库提交前必须已可靠落盘。检查现有 `renameTo()` 返回值，并确保失败不会继续写出指向不存在文件的 `FileEntity`。
- 提交前准备过的 hash 文件如果尚未被 DB 引用，需要受活动租约保护；事务失败只能清理本操作独占的临时资源，不能直接按 hash 删除共享文件。
- 用户消息、全部文件索引和全部图片关系必须一起成功。某张图失败时草稿保留并显示失败项，禁止把“文字成功、图片丢失”当作一次成功发送。
- 若保留现有 `saveFile()` 接口供头像使用，可以内部复用准备／提交能力；聊天新入口不应在选图时留下没有所属消息的永久索引。
- 网络失败发生在本地提交之后，保留已保存的用户消息和图片。重试引用同一消息 ID，只重新发起生成，不再次插入用户消息。
- 停止生成会取消处理和网络协程；若已经提交消息，则保留用户消息、图片以及按现有规则保留的部分回复。

所有写入／释放文件索引的路径都应服从统一的并发顺序：先取得文件存储协调锁，再执行短 Room 事务；不要在已持有 Room 写事务时反向等待该锁。实际网络请求只持有文件读取租约，不长期占用互斥锁。

### 删除、分支与编辑

| 操作 | 数据库内动作 | 事务提交之后 |
| --- | --- | --- |
| 删除单条消息 | 删除覆盖该消息的失效摘要，删除图片关系与附件专属 UUID，再删除消息 | 对候选 hash 检查剩余索引和读取租约，满足条件才回收原图及派生缓存 |
| 清空／删除单聊 | 在消息被删前收集并清理该会话图片关系与 UUID | 按相同规则回收物理数据 |
| 删除群聊 | 扩展 `GroupChatRepository.deleteSession()`，不能只依靠群消息级联 | 同上 |
| 群聊从某条消息重新生成 | 沿用现有 `deleteMessagesFrom()` 的删除范围，同步删除范围内附件 | 已删除图片不会重新混入后续 Prompt |
| 删除角色 | 在角色级联删除单聊会话之前，清理这些单聊的附件 | 不清理仍存在群聊中的用户图片 |
| 创建单聊分支 | 通过现有新旧消息 ID 映射复制关系，为每个附件创建新 UUID 指向同 hash | 原图无须复制；删源会话后分支仍能显示和发送 |
| 修改文字、增加／移除／排序图片 | 同一事务更新正文和图片关系，并使覆盖该消息的摘要失效 | 回收已移除的附件索引对应候选资源 |

附加约束：

- 编辑时允许“空正文 + 至少一张图”；删除全部图片且正文也为空时，拒绝保存并提示删除整条消息。
- 沿用现有编辑／删除使摘要失效的机制；图片替换和顺序调整同样算内容变更，不能继续复用旧视觉摘要。
- 附件读取按当前消息页或 Prompt 候选窗口批量查询，关联的 FileEntity 也批量加载，避免每条消息或每张图片单独查库；长 ID 列表分批查询，使用同一读取事务获得正文及附件的一致快照。
- 页面分页继续使用原有消息排序和游标，附件表不承担消息分页职责；图片数量不改变世界书深度、消息条数和摘要边界的单位。
- 启动或空闲时可清理“父消息已不存在”的异常关系及其专属 UUID；文件回收仅扫描无任何 `FileEntity` 引用、无活动租约且过了宽限期的 hash 文件。不要把所有无 `message_images` 引用的 `FileEntity` 都判作垃圾，头像也使用此表。
- 回收必须与新建引用使用相同协调机制，避免“检查引用为零后，另一个协程创建引用，再被删掉文件”的竞争。

## 图片处理与资源限制

### 原图、缩略图和发送版本各司其职

| 资源 | 保存位置与用途 | 回收规则 |
| --- | --- | --- |
| 原图 | `FileRepository` 的永久 hash 文件；用户查看、归档、重新处理的依据 | 最后一个文件索引和活动租约释放后才可清理 |
| UI 缩略图 | 有容量上限的内存／磁盘缓存，按显示尺寸采样 | 随时可以淘汰，由原图重建 |
| 发送版本 | 可淘汰磁盘缓存；已应用方向校正、尺寸限制和元数据清理 | 缓存淘汰后重建；本次请求进行中保持租约 |

缩略图及发送版本建议仍通过 `FileRepository` 管理的缓存接口访问，不成为新的永久 `FileEntity`，也不占用 `message_images` 行。派生缓存 key 至少包含原图 hash、处理规则版本、目标尺寸、输出格式及质量；不能只按消息 ID 缓存，否则会反复生成相同数据。

原图指应用从系统 URI 实际读取到的完整字节，不能承诺一定是云相册服务未转换前的母文件。保留原图不等于原样上传；网络只能读取处理后的发送版本，禁止失败时回退到未经处理的原图。

处理顺序建议为：读取边界和格式 → 有界采样解码 → 应用 EXIF 旋转／镜像 → 统一色彩和输出尺寸 → 重新编码 → 验证实际 MIME、尺寸和文件大小。方向必须在显示与发送两条路径一致处理。

当前 `loadBitmapForCrop()` 会处理 EXIF，但 `loadSampledBitmap()` 不会；因此不能原样复用后者就认定方向已正确，也不能把正方形头像裁剪流程直接用于聊天图片。

### 建议的首版支持范围与初始限制

下列数值是客户端建议初值，需要通过真机内存测试和真实网关联调调整，不是三家服务商统一限制。

| 项目 | 建议初值或策略 |
| --- | --- |
| 单条用户消息图片数 | 最多 `4` 张，按用户确认的显示顺序发送 |
| 单次请求图片数 | 最多 `12` 张，包含仍在上下文内的历史图片；同时服从请求字节和 Token 预算 |
| 原图输入 | 建议单图最多 `32 MiB`、最多 `48` 百万像素，另设单边界限，使用 `Long` 计算像素乘积 |
| 默认发送尺寸 | 长边最多 `1536 px`，等比例、不放大小图；先验证截图小字和长图质量 |
| 单张发送文件大小 | 建议最多 `2 MiB`，照片优先 JPEG；需要透明度的图片优先 PNG |
| 完整 HTTP JSON 大小 | 建议最多 `16 MiB`，包含 Base64、文字及高级请求扩展；服务商更严格时取更小值 |
| 解码并发 | 默认串行处理大图，预览和发送任务使用有界并发，避免同时驻留多张完整 Bitmap |
| 输入格式 | JPEG、PNG、静态 WebP 作为基础范围；HEIC／HEIF 仅在当前设备可成功解码时接受并转码 |
| 动画／其他内容 | 首版不接入动画播放、视频、PDF 或 SVG；检测动画并明确提示，不静默当静态首帧发送 |

缩放和有损压缩会损失细节，因此发送前应能预览实际发送效果；文字密集长图若处理后不可读，明确提示用户改用局部截图。透明 PNG 超限时可以进一步等比缩小，无法满足限制则保留草稿并失败，不偷偷丢弃透明度。

需要检查的不是 URI 声称的文件大小或 MIME，而是读取到的实际字节及可解码格式。限制必须在复制过程中执行；不能先 `readBytes()` 读完整个超大文件再检查。图片元数据缓存可以按 hash 保存原始宽高、方向、实际 MIME 和长度，不必为此增加第二张业务表。

Base64 长度为 `4 × ceil(原始字节数 / 3)`，例如 `2 MiB` 的发送文件约形成 `2.67 MiB` 的 Base64，还没有计算 JSON 和文本。请求限制必须统计完整历史，不只是输入区新选的几张图。

目前适配器使用 `JSONObject`、字符串化以及 JSON Merge Patch，多次复制请求正文；图片放大了这条链路的内存成本。建议含图请求使用流式 JSON／Base64 写入临时请求文件，再由 OkHttp 读取，同时取得精确字节长度；纯文本可以保留现有路径。Patch 在不含图片字节的结构上完成并继续保护消息字段，最终写出时注入原生内容块，日志独立生成脱敏结构。不能为了流式写出而破坏现有 Patch 语义。

## 对话页面设计

### 输入区

沿用 Material 3、动态配色、现有气泡和底部安全区域，不增加常驻的大附件面板。

```text
既有快捷操作／群聊发言者控制
待发送图片条： [缩略图 ×] [缩略图 ×] [添加]    已选 2 张
输入行：      [图片] [输入下一段故事……]       [发送／停止]
必要时：      图片处理中／某张图片无法读取
```

- 图片入口应直达相册选择器。单聊现有输入框左侧魔法图标与上方快捷条存在重复入口，可将左侧位置用于图片；群聊既有快捷菜单可保留在“更多”入口。
- 无图片时不显示缩略图条，维持当前输入区高度；有图片时横向滚动，缩略图约 `64–80 dp`，不把消息列表挤成小窗口。
- 每张图片有处理状态、移除和点击预览；顺序以条带为准，支持调整顺序，网络序列化不能采用后台任务完成顺序。
- 支持连续添加图片，选择器回调后再次校验剩余数量。取消选择器不影响已有草稿。
- 已选图但尚未处理完成时显示等待状态并禁止提交。失败项允许移除或重试，不清空其他文字和图片。
- 有图片而文字为空时“发送”发送纯图片消息；只有两者都为空才沿用既有空发送／续写行为。
- 群聊纯图发送使用 `isUserInput = true`，关键词激活文本为空；不要拿上一条角色正文替代本次输入。Manual 模式仍要求选择发言者，其他模式沿用既有调度规则。
- 正则处理后正文变空但仍有图片时继续发送图片；仅有文字且被处理为空时不能落成无意义空消息。
- 生成期间保持现有“发送变停止”交互。新图片处理也应可取消，连续点击发送不得产生重复用户消息。

### 选择器和页面状态

通过 Activity 的 `PickMultipleVisualMedia` 并限定 `ImageOnly` 接入。官方契约在不可用设备上回退到 `ACTION_OPEN_DOCUMENT`；回退时系统可能忽略最大选择数量，因此应用必须二次校验。项目现有 Activity 依赖 `1.13.0` 已覆盖所需基础契约，不必因选图本身升级依赖，也不应依赖 Google Play 回补模块才能工作。[Android Photo picker](https://developer.android.com/training/data-storage/shared/photo-picker)

系统 URI 访问权限不是永久文件存储。返回结果后尽快复制到应用私有 staging；确实需要跨进程继续读取时再取得可持久化读权限，并处理来源撤销、云端下载失败和 URI 消失。[Android 媒体访问生命周期](https://developer.android.com/training/data-storage/shared/photo-picker#persist-media-file-access)

遵循项目既有 MVI 规范：

- `UiIntent` 表达添加、选图结果、移除、排序、打开预览和发送等用户行为。
- `ViewEvent` 负责打开系统选择器等 Activity 动作。
- 输入子状态包含文本、图片草稿列表、处理进度和可发送状态；图片查看器放 dialog／viewer 子状态。
- Bitmap 大对象、Base64、输入流、真实文件路径都不进入普通 UiState；ViewModel／图片加载器管理缓存，页面持有资源描述。
- 至少保证配置变更时草稿不丢。进程重建可通过 `SavedStateHandle` 恢复小型草稿描述，恢复前检查 staging 文件；缺失则提示重新选择，不显示“就绪”的假缩略图。长期跨重启草稿仓库不作为本期必需新增功能。
- 单聊和群聊共用选择器协议、附件条、图片网格和查看器；各自保留生成流程，避免为了图片大幅重构两个 ViewModel。

### 消息气泡和预览

| 场景 | 推荐表现 |
| --- | --- |
| 单张图片 | 保持比例展示，限制最大高度，不强制方形裁剪；长图可显示缩略预览与查看入口 |
| 多张图片 | 两列紧凑网格，显示顺序编号；点击后在同组内左右切换 |
| 文字附图 | 同一气泡里先展示图片组，再展示文字正文；不创建多条用户消息 |
| 纯图片 | 仍显示用户名、时间和操作入口，不出现空白正文占位气泡 |
| 大图查看 | 默认适配屏幕，支持缩放和平移；可切换查看原图和发送效果，避免误认两者清晰度一致 |
| 资源损坏或丢失 | 展示固定尺寸失败占位与重试入口；请求若确实保留该图片则报错，不能以占位文字冒充图片 |
| 会话列表预览 | 纯图显示“[图片]”或“[图片 × 张数]”；有文字优先显示文字，必要时附图片标记 |
| 编辑历史 | 同时呈现正文和图片列表，保留未修改图片；使用同一事务保存图文变化 |

图片宽高应在缩略图返回前由元数据确定，列表 item 使用稳定消息 key，防止图片加载后大幅改变高度、破坏分页滚动锚点。只加载可见和邻近范围，不在整段消息转换时解码所有历史图片。

复制文本继续只复制文字；纯图片消息应禁用无意义的文本复制或明确提供“保存图片”。保存、分享原图属于用户显式触发动作，不能在预览时自动写入相册。

## 统一协议设计

### 通用模型使用有序内容块

推荐让 LLM 层 `LLMMessage` 以 `parts` 作为唯一内容来源，而不是长期同时维护可独立修改的 `content` 和 `parts`。以下只是类型草图，不是本次代码变更：

```kotlin
sealed interface LLMContentPart {
    data class Text(val text: String) : LLMContentPart
    data class Image(val image: PreparedImageRef) : LLMContentPart
}

data class LLMMessage(
    val role: LLMMessageRole,
    val parts: List<LLMContentPart>
)
```

`PreparedImageRef` 是请求运行时引用：包含不可变资源标识、处理后 MIME、宽高、字节数、处理规则版本和可由受控 resolver 打开的资源，不把 Android URI、Room Entity 或 Base64 塞进通用消息。

- 为旧纯文本调用提供 `LLMMessage(role, text)` 工厂／辅助构造及只读 `textContent` 投影，降低故事编写、摘要等共享调用的修改成本。
- 文本处理采用明确的 `mapTextParts()` 等语义，只处理 `Text`，不对图片做宏展开、正则或 Think 块解析。
- 持久化消息仍是“正文 + 附件列表”；进入 Prompt 时形成有序内容块，后处理可以在不同来源之间保留图文交错。
- 本期源消息中使用“按 position 排列的图片 + 可选正文”；需要发言者边界时允许先插入短文本标签。
- 不使用 `ImageUrl(String)` 作为唯一图片抽象。本地资源、外网 URL、Provider 的远端 file ID 生命周期不同，应保留独立类型扩展空间。

### 三协议映射

| 协议与现有适配器 | 有图片时的输入 | 纯文本兼容策略 |
| --- | --- | --- |
| OpenAI Compatible：`OpenAICompatibleLLMClient` | `messages[].content` 数组，`text` 块和 `image_url` 块；本地图使用 `data:<mime>;base64,...` | 无图片的消息继续允许 `content` 字符串，照顾兼容网关 |
| Gemini：`GeminiLLMClient` | `contents[].parts` 中使用 `text` 或 `inlineData: { mimeType, data }` | 保留既有 `parts: [{text: ...}]`；角色仍为 `user` / `model` |
| Anthropic Messages：`AnthropicMessagesLLMClient` | `messages[].content` 数组，图片块为 `image`，其 `source` 使用 `base64`、`media_type`、`data` | 纯文本可保持现有字符串输入；system 指令继续进入顶层字段 |

OpenAI Chat Completions 支持 `image_url` 及 Base64 data URL，多张图片可以放进同一 `content` 数组。这里使用项目现有 Chat Completions 格式，不要混入 Responses 的 `input_image` / `input_text`。[OpenAI 图片输入文档](https://developers.openai.com/api/docs/guides/images-vision)

Gemini 的 REST `Part` 使用 `inlineData`，`Blob` 明确包含 `mimeType` 和 Base64 `data`；官方部分示例使用 snake_case，项目手工构造 JSON 时建议统一使用 REST reference 的 lowerCamelCase。[Gemini Part 与 Blob](https://ai.google.dev/api/generate-content#Part)

Anthropic 使用 `image` 内容块，可内联 Base64；官方建议在适合时将图片放在问题文本前面。[Anthropic Vision](https://platform.claude.com/docs/en/build-with-claude/vision)

与现有消息对应的最小片段如下，省略了模型名、生成参数等未变字段。示例中的 `...` 是字节占位，不可直接发送。

```json
{
  "role": "user",
  "content": [
    {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}},
    {"type": "text", "text": "把这张图作为当前场景参考。"}
  ]
}
```

```json
{
  "role": "user",
  "parts": [
    {"inlineData": {"mimeType": "image/jpeg", "data": "..."}},
    {"text": "把这张图作为当前场景参考。"}
  ]
}
```

```json
{
  "role": "user",
  "content": [
    {"type": "image", "source": {"type": "base64", "media_type": "image/jpeg", "data": "..."}},
    {"type": "text", "text": "把这张图作为当前场景参考。"}
  ]
}
```

OpenRouter 官方也支持通过 Chat Completions 的 `image_url` 传 URL 或 Base64，适合继续走现有兼容适配器；这不意味着其他所有自定义网关和模型都支持图片。[OpenRouter 图片输入](https://openrouter.ai/docs/guides/overview/multimodal/image-understanding)

### 为什么首次接入选择内联图片

| 路径 | 适用性与代价 | 建议 |
| --- | --- | --- |
| Base64 内联 | 三个现有协议均能表达；原图留在本地，按请求准备发送数据；历史重复发送会增加流量 | 首版采用，配合派生缓存、预算裁剪和请求大小检查 |
| 服务商 Files API | 可减少反复上传，但要维护账号／服务地址／模型关联、失效与删除策略，各家契约不同 | 有大量历史图片后再做受控优化，不能当永久资源 ID |
| 自建图床或外部 URL | 新增服务、访问权限、链接有效期和图片对外可访问性管理 | 本期不需要 |
| 先 OCR／自动描述再发送文字 | 会丢失视觉细节，多出调用且改变已确认的直接读图行为 | 不作为默认替代路径 |

本地缓存只减少重复处理，不代表模型服务跨请求记住图片。项目直接调用无状态生成接口，图片仍须随保留的历史内容块重新发送；不要因上一轮发过就只发送本地 UUID。

Gemini 当前 Generate Content 图片指南仍给出内联总请求小于 `20 MB` 的限制，因此客户端建议采取更低的完整请求上限，不直接套用其他接口页面的较大限额。[Gemini Generate Content 图片指南](https://ai.google.dev/gemini-api/docs/generate-content/image-understanding)

Anthropic 的图片与请求上限区分直连接口和托管平台，历史图也计入整次请求；本次查阅页面列出直连单图 Base64 上限 `10 MB`、部分托管平台 `5 MB`，标准请求体 `32 MB`。这再次说明不能把新选图片数量当作唯一限制。[Anthropic 图片限制](https://platform.claude.com/docs/en/build-with-claude/vision#image-limits-and-costs)

### 视觉能力检查与错误反馈

将“协议能够表达图片”和“当前模型能够理解图片”分开。

- 建议在模型配置增加图片输入设置：自动／支持／不支持，持久化在现有 `LLMProvider` 配置实体，默认自动。用户只禁止修改两张消息表，该配置字段不受此限制；仍保持 Room version `4`。
- 自动解析结果为 Supported、Unsupported、Unknown。优先采用用户覆盖，其次可信模型目录信息；不要用协议枚举、名字是否含 `vision` 或品牌名称直接判定。
- 当前模型目录模型可扩展可空 `inputModalities`；缺失字段就是未知，不能当作“只支持文字”。OpenRouter 模型目录有输入模态字段，可作为明确来源，但解析应针对实际返回结构。[OpenRouter 模型目录](https://openrouter.ai/docs/guides/overview/models)
- 能力缓存按 Provider 配置、服务地址及 model 区分；更改这些配置后失效。不读取或打印密钥来构造可见缓存 key。
- 当草稿有图且明确不支持时，提交前提示切换模型并保留草稿。历史图则按最终保留的请求检查；已被摘要替代或按预算正常裁掉的图片不导致永久拦截。
- Unknown 允许真实请求，不额外发送有费用的探测请求。遇到明确“模型不支持图片”错误可记录会话级结果；不能把鉴权失败、文件超限、网络错误或所有 HTTP 400 都学习成“不支持图片”。
- 流式和非流式共用同一请求准备与校验入口。普通回复、继续、重生成、扮演用户及摘要都必须经过它。
- 群聊按每个实际发言模型校验；已知不能执行的本轮发言在开始前给出明确提示，未知模型中途失败时保留已有回复并停止本轮后续生成，不重新插入用户消息或自动绕过失败角色。

示例提示应为“当前模型不支持图片，请更换模型后重试”“本次历史图片超过请求限制”“总结模型不支持图片，自动总结已暂停”，而不是原始响应、Base64 或完整请求 JSON。

## Prompt、历史、预算和摘要

### 贯穿全链路，不能只改 HTTP Adapter

```text
消息页／Prompt 历史窗口 + 按消息批量查询附件
    → 领域聚合模型
    → 图片元数据及发送规则预处理
    → ChatPromptBuilder / GroupChatPromptBuilder
    → PromptMessageDraft（有序内容块及来源）
    → 后处理与协议角色正规化
    → 文本 + 图片 Token、图片数、请求字节预算
    → 同源的最终请求与 Prompt Inspector
    → 最终图片引用解析、序列化与网络发送
```

数据库聚合、图片准备和 Prompt 纯逻辑分层；Builder 不直接读文件或解码 Bitmap。图片成本相关的发送尺寸、MIME、字节信息在预算阶段已知，最终编码使用同一处理规则与不可变资源快照。

### 必须保留的语义

- 所有“空消息”过滤改成检查有效文本和图片，重点检查 Finalizer、群聊 `sanitizeHistory()`、协议转换以及各路径重新构造对象的地方；不要把所有 `isBlank()` 机械替换，空模型回复与空摘要仍应保持失败语义。
- Regex Source／Prompt／Markdown、宏和世界书扫描只消费文本；图片不会触发 OCR 或图像标签自动激活世界书。纯图片仍占一个消息深度，但贡献的关键词文本可以为空。
- `{{history}}` 等字符串宏可渲染简短的图片数量标记供阅读，不嵌 Base64，不自动复制图片块。真正附件只来自对应的原生历史来源；字符串占位不表示模型看到了图片。
- Prompt 预设如果移除原生历史段，不能在请求末尾偷偷补图；检查器应说明图片没有随历史进入请求。
- Merge 合并时按原先顺序连接内容块，仅相邻文本块可以按现有双换行规则合并；不要变成“全部文字 + 全部图片”。
- SemiStrict／Strict 只调整角色和插入必要的文本占位，不能丢失原图块。系统内容不允许带用户附件，领先 system 提取阶段若发现非法图片来源应报错。
- SingleUserMessage 模式逐条加入发言者边界文本，再接该条图片和正文；即使原消息是纯图片也要保留归属，不能把所有图片统一追加在整段对话结尾。
- Gemini／Anthropic 当前 `toAlternatingConversationMessages()` 又会合并文本。按上文接口契约，将其提取为有序内容块的公共角色正规化逻辑，在 Finalizer 预算之前执行；未最终化入口复用同一逻辑，禁止在 `isPromptFinalized` 后再次改写内容而使预算失真。
- 高级请求 JSON 继续保护 `messages`、`contents`、`systemInstruction` 等结构字段。图片不能靠用户 Patch 塞进去，否则无法纳入附件生命周期、预算和检查器。

### 三种预算同时约束

图片输入 Token 不是 Base64 的文本 Token。OpenAI 官方按模型、尺寸和 detail 使用不同视觉计量规则，因此不能固定给所有模型套用一个图片公式。[OpenAI 图片成本说明](https://developers.openai.com/api/docs/guides/images-vision#calculating-costs)

推荐抽出 `ImageTokenEstimator` / `MultimodalRequestBudget`：

- 文本继续使用现有 Tokenizer；图片按实际发送尺寸、协议及可识别模型规则估算，再加消息格式开销和回复预留。
- 未识别模型使用明确标注的保守估算，初始可按默认尺寸每图预留 `4096` Token，并支持调整；这是回退估算，不是能保证所有网关都不超限的数学上界。
- 同时统计整次请求图片数量和最终 JSON 字节数。预算最终校验要在 Provider Patch 之后，不能只计算图片二进制。
- 先选择有限的历史候选窗口，用元数据规划；只为可能保留的图片生成发送版本。若实际字节数改变选择结果，重新计算并记录裁剪，真正上传前冻结计划。
- 裁剪按来源消息为单位，正文与它的全部图片一起去留。图片太大时不能保留文字却静默丢图，也不能在一条“比较这四张图”的消息里只留两张。
- 当前用户提交的消息不可因预算被裁掉；群聊本轮后续角色回复时，仍保护触发本轮的用户图文消息，而不仅保护刚生成的最后一条角色消息。
- 必需项本身超出图片数、字节或 Token 上限时阻止请求，提示减图、调整图片或预算；旧历史则沿用保留优先级整体淘汰，并记录原因。
- 重生成沿用其历史边界，不带入目标之后的图片；创建分支后只读取新分支消息 ID 对应的附件。
- `PromptTokenizer.countMessage/countMessages/countMessagesUpTo`、Finalizer 的增量／非增量路径及 `LLMTokenUsageTrackingClient` 的本地回退要共用同一计量规则，不能主请求算图片而摘要或用量统计漏算。

Prompt Inspector 建议显示每条来源的缩略图、图片数、发送尺寸、图片估算 Token、最终入选状态；omitted 增加图片数上限、请求字节上限等原因。服务端报告用量仍按当前用户设置使用，且区分服务端总输入用量和本地视觉估算，避免重复相加。

### 摘要直接读取图片，但继续保存文字摘要

沿用现有摘要表与边界字段，不新增图片描述表，也不在普通聊天里插入一次独立的“图片转文字”模型调用。

推荐的摘要素材结构：

```text
System：现有摘要指令，并要求记录与剧情相关的可见图像信息、明确不确定内容
User：
  Text：已有文字摘要
  Text：消息边界、发言者
  Image：该消息图片甲
  Image：该消息图片乙
  Text：该消息正文
  Text：下一条消息边界与正文
  ……
```

- 将 `buildRawSummaryMessages()` 的纯字符串历史升级为可携图素材，并用于两个摘要 Builder；已有角色名、用户设定和摘要指令模板继续走原来的清洗和宏处理。
- 保留 `summaryCandidates()` 排除最后一条正在变化消息的规则；`selectSummaryPrefix()` 仍选择最早的连续消息前缀，但成本包含图片、总请求大小和图片数量。
- 每个候选前缀必须使用一致且固定的图片处理规则，确保成本单调；不能在二分搜索过程中根据图片总数反复改变所有图片清晰度，破坏现有算法假设。
- 最早一条图片消息过大时可以要求用户调整或停止本次摘要，不能跳过它后把覆盖边界推进到后面的消息。
- 只有模型成功返回非空文字摘要，并且输入消息快照仍有效，才提交新的 `coveredMessageId`。失败、取消、能力不足都不能推进边界。
- 摘要请求在事务外执行，提交前重新检查摘要基线和所覆盖消息／附件快照；并发编辑、删除或摘要恢复后应丢弃过时结果，而不是覆盖新状态。
- 摘要应记住与剧情相关的场景、人物外观、物品及用户指定细节，区分“图片可见”“用户声明”和“不确定”；不要求逐像素描述，也不假设文字摘要能保留所有视觉细节。
- 摘要覆盖后，正常请求按已有边界使用文字摘要和后续图文消息；本地原图不删除。需要重新看已摘要图片细节时可以再次附图，或利用现有摘要恢复／重新总结入口，不默认把全部旧图永久塞回上下文。

当前单聊和群聊都通过 `requireSummaryProvider()` 独立选择摘要模型，不能假设摘要模型与对话模型相同。选中的摘要前缀有图时，必须检查摘要模型能力：已知不支持或明确图像能力错误时暂停当前会话自动摘要并给出一次可操作提示；手动摘要展示失败并保留旧摘要。未知允许尝试。切换摘要模型后由用户恢复或重试，禁止无提示退化成纯文本摘要。

## 日志、故障恢复和数据可携带性

### 请求日志必须排除图片字节

现有 Debug 日志会保存传入的原始 JSON。若只改协议序列化，每轮都会把历史图片 Base64 再写一份日志，既放大存储，也抵消文件仓库去重收益。

- 在日志写入边界统一结构化处理 OpenAI data URL、Gemini `inlineData.data`、Anthropic `source.data`；记录 MIME、尺寸、字节数和图片序号等元数据，二进制用明确的脱敏标记替代。
- 日志与实际请求用不同表示，不能先脱敏再把同一对象发送。脱敏日志要标明“图片数据已省略，不能直接重放”。
- 流式／非流式、成功／错误路径都使用相同规则；对可能回显请求内容的错误响应也要限制长度、处理图片载荷，不能只清理成功请求日志。
- 普通 Toast、异常与崩溃日志不输出 URI、原图路径、图片内容或完整请求。当前 FileRepository 抛出的 URI 错误也需要经统一错误展示映射。
- 单条日志保留大小上限，避免一次大量文本或 Provider 错误回显使详情页无法打开。

### 导入导出不能把本地 UUID 当成可携资源

当前只有单聊文本 JSONL 实现；仓库中的群聊归档文档仍是开发方案，不能把群聊图片包宣称为已有能力。

建议明确两种导出用途：

| 导出形式 | 建议行为 |
| --- | --- |
| 现有 SillyTavern 兼容 JSONL | 保持文本兼容；检测到附件时，导出前明确提示不会包含图片，用户选择文字导出后才继续；纯图消息用可读的遗漏标记表达，不写不可访问的本地 URI |
| RPClient 携图归档包 | 后续以 ZIP 容器保存消息清单和按 hash 去重的原图，提供可恢复的图文备份；不承诺该 ZIP 可被 SillyTavern 直接导入 |

携图包的推荐结构为 `manifest.json + chat.jsonl + assets/<hash>`：manifest 中图片关系使用归档内消息序号与资源 key，另记录 MIME、长度、hash 和 position；导入时创建新消息 ID 和附件专属 UUID，并由 FileRepository 去重。包内只保留每个原图一次，不导出缓存图或任意机器路径。

导入必须验证成员路径、展开总大小、单文件大小、hash、实际图像格式和关联完整性；资源全部准备成功后再提交会话及图片关系。旧文本 JSONL 继续按当前行为读取，不自动下载正文 Markdown 中的外网图片。

文字导出的明确提示应和图片发送同期完成，防止已有按钮静默丢图；完整携图归档可独立交付，但完成前不能宣称图片聊天可以无损导出。归档格式版本与 Room version 是不同概念，前者可以独立定义，不因此升级 Room version。

### 系统备份和文件缺失

当前 Manifest 允许系统备份，备份规则显式排除的是请求日志数据库，并没有因此排除主库和所有原图。新增大量原图后，应验证系统备份／设备迁移是否同时恢复消息关联、文件索引和文件数据；可重建缓存和 staging 应排除在永久备份之外。

本方案不擅自改变项目已有的系统备份偏好，但“应用私有目录”不应被写成“绝不会进入系统备份”。无论恢复来源如何，缺文件都应展示缺失状态，并在含图请求前报错；不要把系统备份当作已经验证过的无损携图导出。

## Room version 保持不变的处理方式

本项目当前 `AppDatabase.version = 4`，`exportSchema = true`，并有 `1→2`、`2→3`、`3→4` 自动迁移。依用户明确要求，图片支持继续使用未发布的 version `4`，不新增 `4→5`，本次调研也不实际改 schema。

后续实现应：

- 将 `MessageImageEntity`、DAO 注册进现有 AppDatabase，并注册相应 Repository／服务。
- 在保持 version `4` 的情况下重新生成并提交 `app/schemas/me.kafuuneko.rpclient.libs.room.AppDatabase/4.json`，如增加模型能力配置字段，也体现在同一 schema 中。
- 保留已有的历史 schema `1.json`、`2.json`、`3.json`。用既有迁移链验证从受支持旧版本迁移到最终 `4` 后，新表存在且老消息保持无图片状态。
- 注意曾安装过旧开发版 `4` 的设备：其旧 schema 与新的 `4` 同版本但结构不同，正常版本迁移不会执行，可能触发 Room identity hash 校验失败。开发／测试安装需要使用经用户安排的数据备份与重建策略；不能宣称“不升级 version 就能直接覆盖所有旧开发库”。
- 不通过关闭校验、篡改 identity hash 或让应用自动删除真实用户数据绕过该问题。文档只是说明验证前提，不执行清数据或重装操作。

项目 Room 数据层规范一般要求结构变化升级版本，本次以用户对“当前版本未发布”的明确指令为准。Room 官方说明自动迁移依赖新旧两侧导出的 schema，因此保持版本号并不意味着可以省略维护最终 schema 和旧版本迁移验证。[Room 数据库迁移](https://developer.android.com/training/data-storage/room/migrating-db-versions)

## 建议实施拆分

以下为设计层面的工作包概览；具体步骤、依赖、验收与逐阶段更新以独立的 [实现任务表](./用户图片发送功能实现任务表.md) 为准，功能实现尚未开始。

| 工作包 | 主要落点 | 完成条件 |
| --- | --- | --- |
| 数据与生命周期 | `libs/room/entity`、`dao`、消息仓库、`CharacterRepository`、`FileRepository` | 图片关系、独立 UUID、文件准备与提交、批量读取、所有删除与分支路径一致 |
| 图片处理 | FileRepository 缓存能力及独立图片处理服务 | 方向、格式、限制、缩略图、发送版本及取消／回收可验证 |
| 多模态协议 | `libs/llm/model`、三个 adapter、请求准备和错误映射 | 纯文本兼容、纯图／多图请求、能力检查、流式和非流式一致 |
| Prompt 和用量 | 两个对话 Builder、Finalizer、PostProcessor、Tokenizer、usage tracking、Inspector | 图片经过所有模式仍保留归属，所有预算路径一致，不静默丢图 |
| 视觉摘要 | 两个摘要 Builder、摘要选择与提交协调 | 连续前缀不漏图，失败不推进边界，摘要模型独立检查 |
| 对话交互 | 两个 Activity、UiIntent／ViewEvent／UiState、布局及共享图片组件 | 选图、顺序、预览、纯图发送、失败重试、编辑和列表预览 |
| 交付闭环 | 日志、文字导出提示、Room schema、依赖注入 | 不在日志重复存图，不静默导出丢图，version 保持 `4` |
| 后续扩展 | 携图归档、远端文件缓存、更多图片质量选项 | 不阻塞上述已确认的数据和协议结构 |

层间依赖以本文“接口契约与层间调用约定”为准：消息 Repository 编排持久化，文件及附件能力提供底层操作；Prompt 使用领域快照，公共请求准备能力供协议发送复用。通用图片处理不依赖 UI；DAO 不持有 Repository；网络层不直接查询 Room。新服务在 `RPClientApp.kt` 使用现有 Koin 方式注册，不引入大型多模态框架。

## 验证重点与验收标准

本次为文档变更，不运行构建、不新增测试。后续实现时优先保护跨模块行为与协议兼容，而不是给普通属性映射堆测试。

| 验证方向 | 必须覆盖的场景 |
| --- | --- |
| 引用与回收 | 相同字节多次发送只保存一份原图；删除其中一个附件或源分支不影响其余；并发保存与回收不删活文件 |
| 事务与恢复 | 多图中途失败、DB 提交失败、落盘失败、取消与进程中断不产生半条图文消息；暂存和孤立物理文件可恢复清理 |
| 删除边界 | 单条删除、清空单聊、删除群聊、角色级联、群聊截断重生成、单聊分支及图片编辑摘要失效 |
| 图像处理 | EXIF 各方向、透明 PNG、静态 WebP、设备不支持的 HEIC、动画检测、损坏文件、伪 MIME、超大像素和云端 URI |
| 协议 | 三种协议 × 流式／非流式 × 纯文本／纯图／多图；顺序、MIME、角色字段、未知能力、接口错误与 Patch 保护 |
| Prompt | None、Merge、SemiStrict、Strict、SingleUserMessage；正文经 Regex 变空；宏重复历史不复制图片；重生成不带后续图 |
| 预算 | 图片数量、完整请求字节和 Token 分别超限；当前用户图文不可拆裁；增量与完整统计一致；未知模型估算标识 |
| 摘要 | 首条图片超预算、纯图消息进入候选、连续前缀覆盖、最后一条排除、独立摘要模型不支持、取消和过时快照不提交 |
| 日志与导出 | 每种协议的 Base64 和错误回显都不写入日志；文字导出明确告知图片遗漏；携图包未来验证跨设备 ID 重映射 |
| 界面和性能 | 小屏／大字体／键盘、旋转与重建、加载后滚动锚点、原图缩放、分页长历史、有界解码及低内存设备 |
| Room | 全新安装及受支持旧版本到最终 `4`；开发版旧 `4` 单独按已知前提处理；不升级 version |

优先扩展已有 `PromptPostProcessorTest`、`PromptRequestFinalizerTest`、`SummaryPromptBuilderTest`、`ChatPromptBuilderTest`、`GroupChatPromptBuilderTest`、`LLMHttpUtilsTest`；文件／数据库跨存储一致性使用仪器测试，沿用 `FileRepositoryThumbnailTest`、`ConversationPageRepositoryTest` 和摘要 Repository 测试的环境。协议 serializer 建议抽成可独立测试的纯逻辑，使用脱敏固定样例，不对真实模型回复内容做脆弱断言。真实联网验证使用可公开的测试图片和用户允许的配置，不读取私密对话作为测试素材；分别记录三协议的实际模型、流式／非流式结果与未验证项。

验收时最有代表性的连续场景是：用户发送两张图片与一句话 → 群聊多个角色或单聊正确引用图片 → 重试不重复插入用户消息 → 创建单聊分支后删除源会话仍可读图 → 摘要读图后保留视觉事实 → 后续上下文使用摘要而不永久携带旧图 → 原图仍可在本地查看，日志没有图片字节副本。

## 调研结论的适用边界

代码事实基于本页列出的提交；官方 API 来源于本次访问，协议字段已核对，但未使用真实账户发送图片、测量网关限制或压测 Android 设备。因此本文是可执行的设计方案，不是兼容性测试报告。尤其是模型视觉能力、图像 Token 估算、清晰度初值、各类第三方网关的请求上限，需在实现阶段按真实配置验证。

图片发送的最小完整闭环同时包含存储、对话交互、协议、历史预算、视觉摘要和删除／重试语义。只加入一个选图按钮并在 HTTP 请求里追加 Base64，无法满足本项目已经具备的分支、摘要、Prompt 后处理和本地数据管理能力。
